# ROI 측정 지연 개선과 남은 한계 — 2026-10-15

**계산 완료 시점의 관측 나이 중앙값은 변경 전 170.66ms에서 변경 후 138.11ms로 감소했다. 최적화 후에도 12개 모두 100ms를 초과해 거부했다. 전체 429개 테스트와 독립 코드리뷰를 통과했으며, 모터 명령은 0회다.**

기준 구현은 `d081281`이다. `feat/fast-observation` 작업 브랜치에 독립 리뷰 후 커밋·푸시했으며 main에는 병합하지 않았다. 이 문서는 그 다음 최적화 단위의 증거다.

## 변경과 유지한 조건

1. `learning/fast_observation.py`: 크기별 고정 템플릿을 기준 프레임 설정 때 생성한다. 매 프레임 중복 후보 검사에서 픽셀 좌표 배열을 생성하는 대신 동일한 제외 사각형 바깥의 네 영역 최대값을 비교한다. 전체 장면·0.8/1.0/1.2 크기 가설 검사를 유지한다. 무작위 200개 경계·홀수 크기 사례에서 기존 전체 mask 방식과 최대값이 정확히 같음을 테스트했다.
2. `learning/fast_probe.py`: 동기식 카메라 GET 한 건의 receipt와 원본 이미지를 영상 계산 직후 저장한다. 계산 전에 디스크 기록 완료를 기다리지 않는다. 다음 프레임 요청은 현재 원본·측정·기록이 저장된 뒤에만 한다. 별도 백그라운드 큐·프레임 드롭은 없다.
3. 요청 전 `capture_requested` 이벤트를 내구성 있게 남긴다. 계산 중 중단돼도 이미 받은 receipt·JPEG는 `finally`에서 저장한다. 기록 실패 시 다음 capture를 진행하지 않으며 완료된 측정으로 세지 않는다. 갑작스러운 프로세스 종료·디스크 고장으로 남은 요청만 있는 경우 성공으로 해석할 수 없다.
4. `accepted`는 **계산 완료 시점**의 판단이다. 원본·측정 파일 저장 이후의 나이는 별도 `persistence/*.json`과 `measured` 이벤트에 기록한다. 이 기록의 `withinAgePolicyAtPersistence`도 확인해야 하며, 이후 이벤트 쓰기·실제 소비까지 추가된 지연은 별도 재검증 대상이다. 모든 제어·학습 적격성은 계속 false다.

100ms 정책, 기준 프레임 15초 제한, 이동 범위·모호성·소실·재부팅 거부 조건은 변경하지 않았다. 계산이 먼저 끝났다는 이유로 나중에 소비한 좌표를 신선한 제어 입력으로 인정하지 않는다.

## 소프트웨어 테스트·독립 리뷰

- 전체 `python3 -m unittest discover -s tests -q`: **429개 통과, 13.686초**.
- 추가 5개 테스트: 네 영역 최대값과 기존 mask의 동등성, 느린 이미지 기록의 별도 나이 판정, receipt 기록 지연 분리와 다음 요청 전 flush, 계산 중 중단 시 원본 보존, receipt 저장 실패 시 다음 요청 차단.
- 별도 리뷰 에이전트가 최종 코드 diff와 호출 경로를 검토하고 관련 테스트 30개를 직접 실행했다. 수정이 필요한 P0/P1/P2 문제는 발견하지 못했다. 리뷰 에이전트는 실물 요청을 실행하지 않았다.
- 현재 GitHub workflow는 push를 main/master에만 연결한다. 작업 브랜치의 실행 목록은 비어 있었으며 이를 CI 통과로 표시하지 않는다. main 병합 제안 전 필요한 CI/통합 검증을 별도로 확인한다.

## 실제 장치 비구동 비교

Pi에서 기준 코드와 최적화 코드를 별도 `/tmp` 디렉터리에 두고 각각 최신 JPEG 12개를 연속 수집했다. OpenCV 4.12.0/스레드 4, 고정된 카메라와 정지한 컵, 기존 perception/ROS/dashboard 실행 상태를 유지했다. 운영 코드·서비스 설정·펌웨어를 변경하지 않았다. 서로 다른 시점의 실제 프레임이므로 완전히 통제된 동일 입력 벤치마크나 지연 상한 증명은 아니다.

| 항목 | 기준 중앙값 | 최적화 중앙값 |
|---|---:|---:|
| CAM 보고 원본 나이 | 52.96ms | 66.06ms |
| HTTP 요청~응답 | 42.62ms | 40.40ms |
| 응답~측정 시작 | 30.78ms | **0.12ms** |
| 영상 계산·검증 | 44.67ms | **36.07ms** |
| 보고 원본 나이 + 요청~계산 완료 | 170.66ms | **138.11ms** |
| 측정 수락 | 0/12 | **0/12** |

최적화 후 계산 완료 나이 범위는 **122.92~159.57ms**다. 원본·측정 파일의 저장 완료 후 나이는 **166.35~200.27ms, 중앙값 181.15ms**였다. 즉 디스크 비용이 사라진 것이 아니라 계산 뒤로 이동했고, 계산·저장·전달을 모두 마친 제어 지연이 100ms 아래로 개선됐다는 증거는 아니다. 기준 버전은 같은 저장 완료 지표를 따로 남기지 않아 그 값의 전후 비교를 주장하지 않는다.

최적화 표본 12개 중 8개는 CAM 보고 나이 + HTTP 구간만으로 이미 100ms를 초과했다. 영상 계산 최적화만으로 현재 경로 전체를 통과시키기 어렵다는 근거다. 이 합은 보수적인 시간 지표이며 실제 광학 촬영 시각을 교정한 값은 아니다.

기준 실행은 원본 13개/artifact 60개/event 14개, 최적화 실행은 원본 13개/artifact 72개/event 26개를 보존했다. Mac 복사 후 모든 artifact hash와 종료 레코드를 재검증했고, 최적화 실행 코드 hash가 현재 코드와 일치했다. 두 실행 모두 출력 로그 동일·모터 명령 0회다. 종료 장치는 IDLE·모터 출력 0, CAM captureFailures=0, Pi 세 서비스 active·NRestarts=0이다.

## 다음 검증과 완료 기준

- **비구동:** 카메라의 촬영 시작~JPEG 가용 시각, 요청 중 대기·전송 구간, 시계 구간 추정의 보수성/오차를 분리해 측정한다. 현재 100ms 기준을 늘리거나 DMA 시각을 응답 시각으로 바꿔서 통과시키지 않는다. 단순 계산 시간 외 실제 소비 시점의 나이도 평가한다.
- **대상 변화:** 사용자가 컵을 손으로 조금 이동·가림·유사 물체 배치한 실물 영상으로 오차와 거부를 확인한다. 현재는 합성 이동과 정지 실물 장면까지만 검증했다. 모터 구동이 필요하지 않다.
- **행동 수집 전:** 시간 교정·M4 측정 구간·명령 journal/MCU 결과 연결·활성 제한 실행의 실물 검증이 필요하다. 원본 시각 및 소비 시점 신선도 조건을 만족하기 전에는 이 측정값을 제어 입력이나 학습 적격 행동 데이터로 사용하지 않는다.
