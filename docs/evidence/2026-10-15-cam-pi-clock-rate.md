# CAM–Pi 시계 변화율 비구동 실측 — 2026-10-15

**약 182초 동안 91개 실제 표본을 수집했다. CAM/Pi 전체 구간 평균 속도 차이의 가능한 범위는 −141.39~+185.38ppm으로, 현재 ±1000ppm 가정 안에 있다.** 약 60초씩 나눈 전체 표본의 세 구간 평균도 같은 가정 안에 들어왔다. 이는 관측 구간의 평균 속도에 대한 근거이며, **100ms 길이의 순간 속도 상한·2µs timestamp 여유·광학 노출 시각의 검증 완료는 아니다.** 제어 가능 또는 물리 교정 완료로 승격하지 않았다.

## 범위와 방법

- production 소스 `2d59a81e92ac09ad361e9f74bb878dfcc7cae078`의 기존 GET 전용 transport·first-send trace·immutable 저장소를 재사용했다. Pi `/tmp/motionbrain-clock-rate-20261015`의 별도 checkout에서 실행했다. production 코드, 100ms 기준, ±1000ppm·0.002ms 가정, 펌웨어, 운영 서비스는 변경하지 않았다.
- 기본 캡처 46개와 fresh 캡처 45개를 번갈아 요청했다. 요청 시작 사이 최소 2초를 두고, 밀린 촬영을 몰아서 수행하지 않았다. 실제 첫~마지막 GET 송신 시각 차이는 182.111초다. 사용자 확인 배터리 분리 상태에서 수행했으며 모터 명령은 0회다.
- 펌웨어 `source_frame_metadata.h`는 `sourceAgeUs = nowUs − capturedUs`를 계산한다. 따라서 원본 정수 헤더의 `capturedUs + sourceAgeUs`는 HTTP 헤더 생성 직전에 읽은 **CAM timer 시각**을 정확히 복원한다. 큰 uptime에서 정밀도를 잃지 않도록 정수를 먼저 더하고 뺀다.
- CAM timer를 읽은 사건은 Pi의 **첫 socket send 직전 시각 L** 이후, **응답 헤더 파싱 완료 U** 이전에 있어야 한다. 네트워크 왕복 지연의 절반을 편도 지연으로 가정하지 않는다. 두 시계의 부팅 원점 차이를 오차로 취급하거나 서로 다른 monotonic 값을 직접 빼서 영상 나이를 만들지 않는다.
- 같은 CAM boot·Pi hostClockId, 원본/frame/hash, fresh 계약, first-send 의미와 timestamp 순서를 확인했다. **검증 대상인 ±1000ppm을 적용하는 `source_age_basis`는 표본 선별에 사용하지 않았다.** 잘못된 receipt/상태 변화는 원본을 가능한 만큼 보존하고 전체 수집을 중단하는 구조이며, 이번 실측은 91개 모두 유효했다.

표본 i와 j의 CAM 시각 차이를 ΔC(초), CAM 차분 timestamp 여유를 ε=2µs라고 하면 해당 사건 사이 **평균 CAM/Pi 속도**의 범위는 다음과 같다.

`(ΔC − ε) / (Uj − Li) ≤ 평균 속도 ≤ (ΔC + ε) / (Lj − Ui)`

모든 분모는 양수이며, 계산은 유리수로 수행하고 출력할 때만 실수로 변환한다. ε는 기존 정책과 같은 크기의 **가정**으로 넣었다. 이 여유를 이번 측정으로 새롭게 교정한 것이 아니다. 이 구간은 신뢰수준 95% 같은 통계적 신뢰구간이 아니라, 인과 경계와 지정한 timestamp 오차 가정으로 계산한 가능한 평균 비율 범위다.
