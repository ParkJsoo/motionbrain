# HTTP 연결 종료와 응답 본문 지연의 구간 분리 — 2026-11-04

[수동 수집 화면](../manual-data-collection.md) · [기존 빈 연결 처리](2026-10-17-idle-http-client.md)

수동 수집의 ARM 응답 유실과 조회 시간 초과를 조사했다. 이번 시험은 인증이 필요 없는 GET만 사용했고 ARM·RUN·모터 명령·촬영은 실행하지 않았다. 앞선 실패 기록과 미확인 저널을 변경하지 않았다.

## 관측 방법과 분모

Mac에서 ESP32로 직접 접속해 기존 urllib 요청과 0.8초 제한을 사용했다. 주소 조회·TCP 연결·전송·응답 헤더·본문 읽기의 시작과 종료를 기록하고, 해당 소켓의 macOS `TCP_CONNECTION_INFO`를 약 25ms 간격으로 읽었다. 패킷 본문 캡처나 펌웨어 업로드는 하지 않았다.

| 묶음 | 한도와 실제 관측 | 결과 |
| --- | --- | --- |
| 기존 제한 계측 | 최대 300요청·180초·실패 3건에서 종료. 실제 256요청, 진단 종료 조회 포함 약 64.49초 | 성공 253, 응답 없는 연결 종료 1, 본문 읽기 시간 초과 2 |
| 지연 복구 관측 | GET 진단에만 최대 4초를 허용, 늦은 본문 사례 1건에서 종료. 실제 69요청 | 완료 68 중 1건은 0.8초 초과, 연결 종료 1 |

두 묶음은 조건이 다르므로 성공률을 합치지 않는다. 4초는 관측용이며 실제 실행의 0.8초 기준을 변경하거나 늦은 응답을 실행 적격으로 승격하지 않았다. 실패를 수집 성공으로 대체하지 않았다.

## 요청 도착 전 연결 종료

256요청 중 한 GET은 TCP 연결이 약 17.4ms, 요청 125바이트 전송 호출이 약 17.6ms에 완료됐다. 그러나 약 170.3ms에 HTTP 헤더를 받지 못하고 상대 연결 종료를 관측했다.

- 종료 직전 송신 버퍼에는 요청 125바이트가 그대로 있었고 수신 확인이 완료되지 않았다.
- 수신 HTTP 데이터는 0바이트, TCP 상태는 상대 FIN 수신을 뜻하는 `CLOSE_WAIT`였다.
- 송신 측 재전송 예정 시간은 239ms였고 재전송은 아직 발생하지 않았다.
- 해당 묶음의 `idleConnectionReleases`는 6에서 7로 증가했다.

이는 **첫 요청 바이트를 100ms 기다리는 서버 정책이 전송 지연·손실의 TCP 복구 기회보다 먼저 연결을 닫는 경로**를 강하게 뒷받침한다. 별도의 지연 GET 시험에서도 첫 전송을 150ms 늦추자 동일한 연결 종료와 카운터 증가를 확인했다. 토큰 오류는 HTTP 403을 반환하는 별도 경로이며, 이번 재현 GET에는 인증 토큰을 사용하지 않았다.

카운터는 전역 값이다. 앞서 유실된 특정 ARM 요청 당시의 패킷은 확보하지 못했으므로 이번 GET 근거를 그 ARM 연결의 직접 관측으로 표현하지 않는다.

## 응답 헤더 이후 본문 재조립 지연

시간 초과 두 건은 다른 구간에서 발생했다. TCP 연결은 약 16.0ms·13.7ms, 응답 헤더는 약 41.3ms·42.9ms에 완료됐다. 요청은 수신 확인됐고 송신 버퍼가 비어 있었다. 이후 본문 읽기에서 0.8초를 넘겼다.

두 소켓은 연결 상태를 유지했지만 본문 중 순서 밖 데이터 2,013바이트·1,436바이트가 도착한 뒤 수신량이 멈췄다. 헤더 185바이트 이후 앞선 데이터 구간이 채워지지 않아 TCP가 본문을 순서대로 전달하지 못한 상황이다. `rxOutOfOrderBytes`는 누적 계수이므로 이를 현재 버퍼 크기로 단독 해석하지 않고, 시간별 수신량·본문 읽기 대기와 함께 판정했다.

진단용 4초 관측에서도 같은 형태를 잡았다. 한 GET에서 헤더는 210.2ms에 완료됐지만, 본문 3,448바이트 중 뒤쪽 2,012바이트만 먼저 관측됐다. 앞선 1,436바이트 구간이 채워진 뒤 **1.889초에 전체 JSON 읽기가 완료**됐다. 새로운 HTTP 요청을 보내지 않고 같은 응답을 계속 읽은 결과다.

따라서 이 시간 초과의 지연 구간은 주소 조회·인증·JSON 처리나 응답 헤더 생성 대기가 아니라 **응답 본문의 TCP 재조립 대기**로 확인됐다. 뒤늦게 도착한 데이터가 원래 패킷인지 TCP 재전송 패킷인지는 패킷 계측 없이 구분하지 않는다.

## 확인된 범위와 다음 수정 경계

요청 쪽 전송 지연과 100ms 연결 정리의 충돌, 응답 쪽 순서 구멍 복구가 0.8초를 넘는 현상을 분리했다. 물리적인 손실·지연 위치가 Mac 무선·AP·ESP32 무선/드라이버 중 어디인지는 아직 특정하지 못했다. 직접 연결도 오류가 발생하므로 SSH 터널 제거만으로 해결됐다고 판단하지 않는다.

첫 바이트 제한은 정상 요청의 복구 기회와 빈 연결이 다른 요청을 막는 시간의 균형을 검토해야 한다. 본문 지연은 상태·출력 조회 경로의 응답량과 전송 특성을 별도로 다뤄야 한다. 대기 조회와 실제 구동 중 검사를 구분하며, 전체 실행 제한 확대나 ARM 자동 재전송으로 오류를 숨기지 않는다. 이 조사에서는 해당 정책·펌웨어를 변경하지 않았다.

최종 별도 조회에서 같은 부팅·IDLE·5축 출력 0·빈 큐를 확인했다. 출력 이력은 순번 28까지, 마지막 명령 ID는 10으로 조사 전과 같았다. 원본 요청·시간·TCP 상태 기록은 로컬에 보존했다.
