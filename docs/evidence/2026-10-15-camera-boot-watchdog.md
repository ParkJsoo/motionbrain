# ESP32-CAM 통신·부팅 진단 — 2026-10-15

[데이터·관측 계약](../data-pipeline.md)

Wi-Fi panic, 지속 무응답, 최초 부팅의 watchdog 리셋을 조사했다. **세 현상이 같은 원인인지는 미확정이며 watchdog 근본 원인도 확정하지 못했다.** 반복 부팅에서 재현되지 않은 문제와 실제로 확인해 수정한 설정 오류를 구분한다.

## 확인한 오류

| 항목 | 확인한 동작 | 수정과 검증 |
| --- | --- | --- |
| 초기 STA 호스트명 | Arduino2.0.17에서 `WiFi.mode()` 뒤 `setHostname()`은 캐시만 바꿈. 진단10회 모두 요청 이름과 실제 이름 불일치 | hostname을 mode 앞에 설정. 수정 진단5/5 일치 |
| 소켓 타임아웃 단위 | `WiFiClient::setTimeout(uint32_t seconds)`에750을 전달해 의도한750ms가750s가 됨 | Stream750ms, 소켓 `tv_sec=0`, `tv_usec=750000`. 실제 설정값20개 일치 |

타임아웃 설정 실패 시 JPEG 전송을 시작하지 않고 프레임 반환·연결 종료 경로를 따른다. SDK 쓰기의 select/retry 때문에 소켓 설정만으로 모든 전송을750ms 또는 외부2초 안에 끝낸다고 보장하지 않는다. 이 오류가 과거 panic·무응답·watchdog의 원인이라고 확정하지 않는다.

## 반복 결과

당시 QVGA / JPEG quality15, Arduino2.0.17 / ESP-IDF4.4.7, 같은 고정 카메라·USB 환경에서 EN/RTS 리셋으로 비교했다. 전원 재인가 시험은 아니다.

| 구성 | 부팅·서버 준비 | 관찰 중 비의도 리셋·panic | 회차 말 이미지 |
| --- | ---: | ---: | ---: |
| 변경 전 | 10/10 | 0 | 9/10 |
| 변경 전 + 진단 계측 | 10/10 | 0 | 9/10 |
| 수정 + 진단 계측 | 5/5 | 0 | 5/5 |
| 최종 수정 | 5/5 | 0 | 5/5 |

변경 전 두 통신 실패는 각각 타임아웃과 일부 본문 수신이었다. 그 시점에 watchdog 리셋은 없었다. 수정 후 별도120초 Pi 통합 표본은 이미지80/80·상태24/24, 비의도 리셋·panic0이었다. 유한한 정상 표본이며 장기 안정성 증거는 아니다.

## 미해결 범위

- 최초 `TG0WDT_SYS_RESET`에는 원인 태스크·PC를 특정할 backtrace가 없었다. [ESP-IDF watchdog 설명](https://docs.espressif.com/projects/esp-idf/en/v4.4.7/esp32/api-reference/system/wdts.html)과 reset reason만으로 사용자 함수·전원·SDK 중 원인을 확정할 수 없다.
- 기존 펌웨어 비교와 반복 리셋에서 재현되지 않았다고 최초 장애가 없었던 것은 아니다. 계측도 타이밍과 메모리 배치를 바꾼다.
- USB 직결 대조, 부팅·RF 시작 순간 전압, 반복 cold power-cycle 측정은 남아 있다.
- 원본 UART·장치 상태·업로드 기록·진단 패치는 로컬에 보존한다. 장치 고유 주소와 일회성 실행기는 공개 문서에 포함하지 않는다.
