# 빈 HTTP 연결의 지연 재현과 수정 — 2026-10-17

[포트폴리오](../../PORTFOLIO.md) · [진단 도구](../../OPERATIONS.md#상태-점검과-진단)

제어기 상태 조회가 간헐적으로 실패해 하나의 재현 가능한 연결 처리 경로를 분리했다. 이 수정은 빈 연결 대기에 한정되며 모든 HTTP 타임아웃을 해결하지는 않았다.

## 재현과 원인

빈 TCP 연결을 1.2s 유지하고 150ms 뒤 상태 GET을 보냈다. 패킷 메타데이터에서 GET은 약 6.7ms에 연결하고 142바이트를 전송했으며, 약 238ms 뒤 전체 요청의 ACK를 받았다. HTTP 응답은 없었고 빈 연결 종료 후 리셋됐다. 전체 시간은 1198.4ms였다.

Arduino WebServer 2.0.17은 현재 클라이언트 하나를 처리하면서 첫 HTTP 바이트를 최대 5000ms 기다릴 수 있다. 재현 결과는 빈 클라이언트의 서버 대기 문제를 뒷받침하지만 무선·드라이버 영향을 모두 배제하지는 않는다.

## 변경

프로젝트 내부 `IdleConnectionWebServer`는 `HC_WAIT_READ` 상태에서 읽을 바이트가 없는 접수 연결만 100ms 뒤 해제한다. SDK가 끊어진 연결을 정리하고 다음 루프가 다른 클라이언트를 받게 한다. 인증·라우트·요청 파서·모터 명령 유효기간은 변경하지 않았다. 공유 SDK도 수정하지 않았다.

`GET /routine`의 `diagnostics.http.firstByteWaitMs`와 `idleConnectionReleases`로 설정과 해당 해제 경로를 확인한다. 일부 헤더·본문, 응답 쓰기는 기존 SDK 타임아웃을 사용하므로 전체 요청 지연의 상한은 아니다. 첫 바이트가 늦는 정상 클라이언트도 닫힐 수 있다.

## 결과

| 항목 | 관찰 |
| --- | --- |
| 동일 빈 연결 시험, 수정 전 | 1198.4ms 후 연결 리셋 |
| 동일 시험, 수정 후 | 대기 GET 39.4ms에 성공 |
| 인증된 기본 속도 설정 12회 | 모두 성공, POST 최대78.947ms; 모터 구동 없음 |
| 후속 실물 단계 | 명령·STOP 응답 후 최종 상태 GET 약830ms 타임아웃이 남음 |

수정 후 빈 연결 시험은 처음과 끝의 명령·부팅·모터 출력 이력이 같았다. 해제 카운터 증가는 전역 값이므로 특정 소켓의 정확한 물리적 100ms 기한을 증명하지 않는다. 후속 타임아웃 뒤 별도 조회에서 IDLE·모터5개 OFF를 확인했지만 원래 검사 실패를 성공으로 바꾸지는 않았다.

네이티브 테스트는 99/100ms 경계, 읽기 가능한 요청, 연결 종료, 시간 카운터 순환, 대기 요청과 연속 빈 클라이언트를 검사한다. 실제 SDK 호환성은 ESP32 빌드로 확인했다. 수정 커밋은 `2a98159`다.

## 한계

- 간헐 HTTP 지연은 미해결이며 명령 응답이 불확실할 때 자동 재전송하지 않는다.
- 명령 합격 기준0.8s와 진단 수집 타임아웃2s를 구분한다.
- 영상100ms·앵커15초·저장250ms 기준은 바뀌지 않았다.
- 패킷 메타데이터·원본 장치 상태·작업 로그는 로컬에 보존하며 이 문서는 재현 조건과 집계를 제공한다.
