# 빈 HTTP 연결과 제어기 타임아웃 — 2026-10-17

## 관찰

영상 기반 파지 시도 중 기본 속도 POST가 기존 0.8s 요청 한도를 넘어 ARM이나 관절 명령 전에 중단했다. STOP 응답은 성공했지만 누락된 POST 응답 때문에 엄격한 명령 추적을 완성할 수 없었다. 이후 상태는 IDLE·모터 5개 OFF였고 새 비영(0이 아닌) 모터 출력은 없었다. 이 시도에서 파지는 완료하지 못했다.

후속 진단은 ARM이나 모터 명령 없이 진행했다.

- 고정된 존재하지 않는 경로에 인증 없는 POST를 순서를 교차해 32쌍 보냈고 모두 0.8s 이내였다. 폼 본문 방식 최대 141.430ms, 쿼리·빈 본문 방식 최대 96.322ms였다. 인증된 명령 처리를 검증한 결과는 아니다.
- 이후 최초 `GET /status`는 158.874ms에 연결해 즉시 요청을 보냈지만 응답 헤더를 기다리다 타임아웃됐다. 진단 수집 타임아웃은 2s, 전체 시간은 2161.848ms였다. 원래 0.8s 합격 기준은 완화하지 않았다. 계획한 빈 연결을 만들기 전에 발생한 실패다.
- 별도의 유한 시험에서 빈 TCP 연결 하나를 1.2s 유지했다. 150ms 뒤 시작한 상태 GET은 1415.0ms 후 연결 리셋으로 실패했다. 처음과 끝의 상태는 IDLE였고 명령 식별값·부팅 식별값·출력 이력은 같았다. 최종 상태 조회는 성공했다.

비공개 빈 연결 시험 도구는 처음에 변화하는 `ageMs`까지 포함한 `lastCommand` 전체를 비교해 `unchangedIdleVerified=false`를 보고했다. `seen/id/type/source/executedAtMs/success`를 비교하자 명령 식별값이 같음을 확인했다. 원본 결과는 보존했다. 앞선 시험 도구는 최초 GET 실패 후 기준 변수가 누락되는 문제도 있었으며, 그 실행에서는 빈 연결을 열지 않았다. 이 두 문제는 시험 도구의 오류이며 제어기 장애로 계산하지 않는다.

패킷 메타데이터를 포함한 추가 32쌍 비교도 통과했다. 폼 최대 89.176ms, 쿼리 최대 101.113ms였고 수집기는 정리 시점까지 동작했다. 941개 패킷을 수집했고 커널 누락은 0개였다. 별도 빈 연결 시험에서는 패킷 메타데이터로 실패를 재현했다. 대기 GET은 약 6.7ms에 연결해 142바이트 요청을 보냈고 약 238ms 뒤 전체 요청 바이트의 ACK를 받았지만 HTTP 응답은 오지 않았다. 빈 연결이 1.2s에 닫힌 뒤 GET이 리셋됐으며 전체 시간은 1198.4ms였다. 127개 패킷, 커널 누락 0개였고 최종 상태·명령 식별값·부팅·모터 출력 이력은 그대로였다.

이 추적은 빈 연결 상황의 서버 대기·연결 처리 문제를 뒷받침한다. 최초 간헐적 실패의 유일한 원인을 확정하거나 모든 무선 영향을 배제하지는 않는다. 최초 패킷 수집기는 분리된 프로세스 세션에서 터미널의 sudo 인증을 사용할 수 없어 요청 전송 전에 실패했다. 기존 터미널 세션을 유지해 수집을 진행했다. 원본 패킷, 인증 헤더, 무관한 UI 연결은 기록하지 않았다. 텍스트 메타데이터에는 고정 진단 요청 줄이 포함되며 전용 진단 소스 포트로 필터링했다.

## 변경

Arduino WebServer 2.0.17은 현재 클라이언트 하나를 받아 첫 HTTP 바이트를 최대 5000ms 기다릴 수 있다. 프로젝트 내부 `IdleConnectionWebServer` 어댑터는 상태가 `HC_WAIT_READ`이고 읽을 바이트가 없을 때만, 접수한 클라이언트를 100ms 뒤 해제한다. 기반 구현이 끊어진 클라이언트 문맥을 정리하며 다음 루프가 새 클라이언트를 받을 수 있다. 리스너·라우트 처리·인증·요청 파서·모터 명령 유효기간 로직은 바꾸지 않았다. 공유 PlatformIO 의존성도 수정하지 않았다.

`GET /routine`에 `diagnostics.http.firstByteWaitMs`와 `diagnostics.http.idleConnectionReleases`를 노출했다. 카운터는 연결별 시리얼 로그 없이 이 해제 경로만 집계한다.

전체 HTTP 지연의 상한을 보장하는 변경은 아니다. 일부만 도착한 헤더·본문과 응답 쓰기는 여전히 SDK 파서·타임아웃을 사용한다. 정상 연결도 첫 바이트가 100ms 넘게 늦으면 닫힐 수 있다. 응답이 불확실한 제어 명령을 자동 재시도하지 않는다. 영상100ms·앵커15s·저장250ms·명령0.8s 기준은 유지하며 이 진단은 학습 적격 자료가 아니다.

## 소프트웨어 검증

- Espressif32 6.12.0 / Arduino 2.0.17로 ESP32 릴리스 빌드 통과. RAM 65048바이트, 플래시 1104289바이트.
- 새 네이티브 어댑터, 모터 출력, 제한 행동·서비스, 대시보드 인증, 보호된 루틴 계약, HTTP 진단 등 관련 테스트 58개 통과. 루프백 서버 테스트는 샌드박스 바인딩 실패 후 네트워크 권한을 받아 재실행했다.
- 네이티브 어댑터 검사는 99/100ms 경계, 이미 읽을 수 있는 요청, 연결 해제·종료 중 클라이언트, millis 순환, 대기 중 실제 요청, 연속된 빈 클라이언트를 포함한다. 최소 모의 전송 객체를 사용하며 실제 SDK 호환성은 ESP32 빌드로 확인한다.
- 독립 읽기 전용 검토에서 최종 구현과 주변 SDK 정리 경로에 남은 P0/P1/P2 문제는 없었다.

## 승인된 배포와 실물 검증

사용자가 메인 ESP32 펌웨어 업로드 한 번을 명시적으로 승인하고 로봇팔 배터리 OFF를 확인했다. 다시 식별한 CP2102N 제어기에 커밋 `2a98159`를 한 번 업로드했다. 64.51s에 완료했고 플래시 해시 검증 후 재부팅했다. 애플리케이션 이미지 SHA-256은 `447b75f5d7be022f17b2b8ab412f062f7a2cb40fe26efd070e790ad097796cfd`였다. Pi 서비스 재시작, CAM·STM32 펌웨어 업로드는 하지 않았다.

새 부팅 상태에서 모터 5개를 OFF로 두고 기존 브라우저 탭을 연 채 검증했다.

- 동일한 1.2s 빈 클라이언트 시험에서 대기 상태 GET이 39.4ms에 완료됐다. 변경 전은 1198.4ms 후 리셋이었다. 빈 연결 해제 카운터는 1→2로 늘었다. 전역 카운터이므로 해당 소켓만의 해제라고 특정하거나 정확한 물리적 100ms 기한을 증명하지는 못한다.
- 처음과 끝의 명령 식별값·부팅·모터 출력 이력이 같았다. 시험 요청 아홉 개 모두 0.8s 미만이며 `/routine` 사전 조회는 44.8ms였다. 당시 진입 검사에 이 요청 시간이 포함되지 않아 이후 따로 확인했다.
- 인증된 기본 속도100 요청 12개가 모두 성공했다. POST 최대 78.947ms, 주변 상태 조회까지 포함한 최대 359.034ms였다. 최종 IDLE, 모터 출력 불변, 정확한 명령 순서를 확인했다. 이 검증에서 ARM이나 관절 요청은 보내지 않았다.
- 재현된 빈 클라이언트 경로와 유한한 정상 명령 표본을 검증한 것이며 모든 통신 실패를 해결한 것은 아니다.

## 이후 영상 기반 파지 중 남은 실패

사용자가 배터리 ON을 확인한 뒤 새 진입 검사를 통과한 영상 기반 접근을 실행했다. 펌웨어 변경 후 열한 번째 구동 요청인 두 번째 집게 닫기 펄스는 명령 응답과 STOP 응답에 성공했지만, 뒤따른 최종 `/status` GET이 약 830ms 뒤 타임아웃됐다. 해당 실물 단계는 종료하고 자동 재개하지 않았다.

구동 응답은 약 43ms, STOP은 약 150ms였다. 별도 읽기 전용 확인에서 IDLE·모터 5개 OFF·큐 0·동일 부팅·동일 STOP 식별값을 확인했다. 사후 출력 감사에서는 의도한 M1 닫기 출력만 442ms 동안 나타났다. 원래 최종 검사 실패는 이후 확인과 구분해 보존했다. 립밤은 여전히 서 있었고 들기나 성공한 파지는 확인하지 못했다.

따라서 빈 클라이언트 수정은 재현 시나리오에 효과가 있지만 간헐적 HTTP 지연은 미해결이다. 모터를 모두 OFF로 둔 채 추가 유한 GET 전용 패킷 추적을 시작했다. 기준을 완화하거나 학습 적격 자료를 생성하지 않았다. 추가 펌웨어 업로드 전에는 별도 승인이 필요하다.

이 단계의 기록 당시에는 검토된 수정이 작업 브랜치에만 있었고 main에는 병합·푸시하지 않았다. 작업 브랜치 push CI는 설정돼 있지 않으며 워크플로는 main/master push, PR, 수동 실행에서 동작한다. 로컬 테스트·빌드 성공은 CI 성공이 아니다. 이후 검증 결과는 [당일 통합 현황](2026-10-17-integration-status.md)을 참고한다.

## 경로 비교와 영상 제어 계속

GET 전용 유한 비교는 0.8s 기준, 진단 수집 타임아웃 2s, 재시도 0회, 기존 UI 탭을 유지했다. Pi의 두 실행은 네트워크 타임아웃이 아니라 미리 정한 세션 예산 80s에 도달해 끝났다. 완료한 요청은 모두 통과했고 최종 IDLE·명령 식별값·부팅·출력 이력은 그대로였다.

| 경로 | 시작·종료 포함 상태 요청 수 | 전체 시간 중앙값 / p95 / 최대 ms | 연결 시간 중앙값 / p95 / 최대 ms |
| --- | ---: | ---: | ---: |
| Pi, 기존 Wi-Fi 절전 ON | 107 | 155.9 / 364.2 / 390.1 | 76.7 / 330.0 / 333.2 |
| Pi, 임시 절전 OFF | 109 | 127.9 / 362.4 / 394.7 | 75.2 / 329.3 / 359.5 |
| Mac 직접 경로, 이후 유한 표본 | 42 | 101.5 / 146.8 / 157.3 | 71.5 / 81.8 / 87.4 |

Pi 절전 OFF로 관찰 지연이 뚜렷하게 개선되지 않아 ON으로 복구했다. 진단을 위해 공식 Ubuntu `iw` 패키지를 설치했으며 서비스 재시작은 필요하지 않았다. Pi 패킷 수집기의 커널 누락은 0개였다. 순차 표본이므로 AP·ESP32·드라이버 중 원인을 분리하거나 잔여 타임아웃 해소를 증명하지 않는다.

이후 Mac 직접 경로에서 인증된 기본 속도100 요청 12개가 통과했다. 주변 상태 조회 포함 최대 103.638ms, 명령 순서는 정확했고 출력은 변하지 않았다. 새 진입 검사와 독립 검토한 비공개 실행기는 동일 0.8s 한도, 750ms 수동 명령 유효기간, 단계별 STOP, 출력·부팅·명령 추적 검사, PWM 상한을 사용했다. 잘못된 인증 값을 출력 없이 거부하는 경우를 포함해 모의 테스트 17개가 통과했다. 임시 인증정보는 증거 보관에서 제외했다.

이후 Mac 경로의 단일 관절 요청 11개가 최종 IDLE·출력 감사를 마쳤다. 어깨·팔꿈치·손목 조정으로 접근했지만 짧은 들기 확인 세 번에서 립밤을 들지 못했다. 닫기 요청 하나는 PWM40을 목표로 했으나 출력 상승이 늦게 시작해 PWM20까지만 도달했다. 구동 응답은 694.3ms, 비영 출력은 302ms였다. 이는 PWM40의 파지력 부족 증거가 아니다. 별도 닫기는 PWM40에 도달해 520ms 유지했고 이후 닫기·들기 확인을 추가했다. PWM 상한은 올리지 않았다. Mac에서도 일부 후속 요청 지연이 0.8s에 가까워, 유한 검증을 거친 대체 경로일 뿐 통신의 완전한 해결은 아니다.

사용자의 추가 사진 전 상태는 모터 5개 OFF·빈 큐·어깨 218.23도였고 립밤은 여전히 서 있었다. iPhone에서 뒤쪽 집게 날이 가려지고 근접 카메라도 물체가 두 날 사이인지 확정하지 못해, 추가 접근 전 외부 깊이 관찰 한 번을 요청했다. 당시 성공한 파지는 미확인이었고 학습 적격 에피소드는 없었다. 영상100ms·앵커15s·저장250ms는 유지했다.

## 영상으로 확인한 파지와 들기

사용자가 제공한 비스듬한 사진 세 장에서 목표가 열린 집게 입구 근처에 있음을 확인했고, 수정한 위치에서 닫아도 된다는 확인을 받았다. 제한된 어깨 내림 펄스 두 번으로 삽입 깊이를 늘렸다. 집게 PWM40 상한과 별도 750ms 닫기 요청을 유지하고 매번 영상을 확인했다. PWM 상한을 올리지 않았다.

마지막 닫기 두 번의 비영 드라이버 출력은 711ms와 703ms였다. 이후 어깨 올림에서 물체가 함께 움직였고, 두 번째 올림에서는 립밤 바닥과 책상 사이 간격 및 집게에 매달린 상태를 확인했다. 이후 iPhone 관찰에서도 STOP 뒤 물체가 유지됐다. 마지막 두 들기 출력은 요청 PWM60 상한에서 474ms와 712ms였다.

별도 읽기 전용 확인에서 IDLE·모터 5개 OFF·큐 0·활성 제한 행동 없음·동일 부팅·최종 STOP 148을 확인했다. 네 요청 모두 0.8s 미만이고 최대 131.0ms였다. 최종 어깨 측정은 218.23도였다. 이 시점까지 Mac 경로의 단일 관절 요청 20개가 최종 IDLE·출력 감사를 마쳤다. 유한한 결과이며 모든 간헐적 HTTP 지연의 해결을 뜻하지 않는다.

독립 읽기 전용 검토에서 이미지 순서가 실물 파지·들기를 뒷받침하고, 원본 출력이 최종 STOP·모든 모터 OFF를 뒷받침함을 확인했다.

사용자의 추가 시점과 정렬 확인을 받은 영상 기반 실물 파지·들기 시연 한 번이다. 학습된 자율 정책, 보정된 파지력, 반복 신뢰성, 학습 적격 동기화 에피소드의 증거는 아니다. 비공개 이미지와 명령·출력 기록은 별도 보관하며 토큰이나 원본 사진을 Git에 공개하지 않는다. 당시 main은 변경 전이었다. 후속 반복은 [립밤 반복 기록](2026-10-17-lipbalm-repetitions.md)에 정리했다.
