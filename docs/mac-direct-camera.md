# Mac 카메라 계측

[데이터 계약](data-pipeline.md) · [운영 안내](../OPERATIONS.md)

`tools/probe_mac_camera.py`는 명시적으로 선택한 연속성 카메라에서 유한한 프레임을 수집하고 픽셀·메타데이터·영속 저장을 검사한다. macOS 14 이상과 맞는 Xcode SDK가 필요하며 Python 감사는 플랫폼과 무관하다. 모터 명령·모델 학습은 수행하지 않는다.

## 현재 역할

이 문서는 재사용 가능한 카메라 도구와 날짜별 계측 결과를 설명한다. [시각 행동 학습](visual-action-learning.md)에는 별도의 [행동 기록 코어](visual-action-collection.md)가 있다. 실제 생산자 연결은 아직 없으므로 아래 21프레임 진단을 실행하면 행동 데이터가 자동 생성되는 것은 아니다. 날짜별 결과는 해당 구도·시계·계측 조건의 기록으로 읽는다.

## 사용

```sh
mkdir -p .local/bin
bash tools/macos/build_camera_probe.sh .local/bin/mac-camera-probe
python3 tools/probe_mac_camera.py list --helper .local/bin/mac-camera-probe
python3 tools/probe_mac_camera.py capture --helper .local/bin/mac-camera-probe --device-id '<Continuity Camera ID>' --view-id '<new-view-id>' --output 'datasets/mac_camera/<new-run>'
python3 tools/probe_mac_camera.py audit 'datasets/mac_camera/<new-run>'
```

Python 래퍼가 독립 프로세스 기한을 적용한다. 기존 디렉터리 덮어쓰기·재개·자동 재시도·다른 카메라 대체는 없다. 이 도구의 검증된 입력은 iPhone 연속성 카메라로, 고정·잠금·Mac 신뢰 설정이 필요하다. 케이블 연결만으로 실제 USB 영상 전송을 증명하지 못하므로 `transportVerifiedUSB=false`다. [Apple 요구사항](https://support.apple.com/en-us/102546)

## 고정 계약

- 시작 최대 30초, 준비 1초 또는 콜백 30회 중 먼저 도달하는 값.
- 기준 한 장 + 평가 20장, 측정 최대 10초, 프로세스 45초 + 종료 유예 2초.
- 요청 형식 640×480 BGRA. 실제 크기·행 배치·회전·반전·프레임 형식을 기록하며 변경 시 중단한다. 늦은 콜백은 버리고 개수를 기록한다.
- 행 패딩 없는 BGRA를 보존하고 밝기 `(77*R + 150*G + 29*B)/256`를 재계산한다. 센서 RAW나 의미 기반 물체 검출이 아니다.
- 이미지·메타데이터 생성, `fsync`, 재읽기, 디렉터리 `fsync`의 전체 트랜잭션을 250ms로 제한한다. 이후 최종 기록·오프라인 감사 시간과 구분한다.
- 저장 실패, 잘못되거나 중복·역행하는 PTS, 장치 단절, 구성 변경, 기한 초과는 실패로 남기며 부분 파일도 보존한다.

CoreMedia 시계에서 PTS를 변환하고 callback·처리·저장 시각을 기록한다. `captureProcessingPassed`는 21장 무결성·저장 통과와 평가 20장 완료, 그중 최소 16장의 PTS→처리 100ms 및 기준 PTS 나이 15초 조건을 요구한다. 기준 프레임은 의미 기반 물체 앵커가 아니다. 표시 시각과 callback으로 광학 노출 시각을 입증하지 못하므로 `overallPassed`, `captureHostBoundsCalibrated`, `controlEligible`, `trainingEligible`은 false다.

## 제어기 상태와 함께 보관

```sh
python3 tools/probe_mac_controller.py --controller-url 'http://<controller-host>' --helper .local/bin/mac-camera-probe --device-id '<Continuity Camera ID>' --view-id '<new-view-id>' --output '.local/observation/<new-run>'
python3 tools/probe_mac_controller.py --audit '.local/observation/<saved-run>'
```

이 도구는 새 촬영 한 번과 읽기 전용 제어기 응답을 묶는다. 촬영 전 네 GET(`/status`, `/sequence`, `/actions`, `/action_outputs`), 첫 프레임 파일 확인 후 카메라 프로세스가 살아 있는 동안 `/status` 여섯 번, 완료 후 같은 네 GET으로 최대 14회다. 요청마다 800ms, 관측 단계 50초, 카메라 래퍼 47초를 적용한다. 프로세스 정리는 TERM·KILL 각각 최대 2초이며 최종 오프라인 감사·봉인과 함께 관측 시간에서 구분한다. 요청을 반복하거나 기존 실행을 재개하지 않는다. 권한은 실행한 터미널 앱에 따라 달라질 수 있으며, 권한 실패는 프레임 0장의 별도 실패로 보존한다.

IDLE·모터 다섯 개 OFF·빈 시퀀스·센서 준비 상태를 검사하고, 전후 부팅 ID와 출력 이력이 같아야 `status=recorded`다. 저장 실패나 250ms 초과, 통신 실패, 구동 상태, 조기 촬영 종료는 후속 요청을 중단한다. 카메라 래퍼와 자식 프로세스도 종료하며 부분 파일은 남긴다. 이 관측 도구에는 ARM·모터 명령·OFF 명령 경로가 없다. 다른 실행기가 구동한 상태를 감지했을 때도 자체적으로 로봇을 정지시키는 도구는 아니다.

원래 응답 본문·요청/수신 시각·해시와 영상 원본을 보관한다. M4의 보고 나이에 요청 왕복 시간을 더한 진단값과 20ms 이내 개수를 기록하지만, CoreMedia·Python 단조 시계·MCU 시각을 합치거나 각 영상에 센서 값을 대응시키지 않는다. 카메라 **프로세스**와 조회가 겹친 사실은 광학 노출과 센서 샘플의 동시성을 증명하지 않는다. 과거 누적 출력 누락 수가 변하지 않았더라도 학습용 출력 이력 적격 판정은 아니다. 감사는 원본 해시·응답·순서·부팅·출력·M4 요약과 카메라 진단을 재검사하며 학습·구동 적격은 항상 false다.

## 2026-10-17 새 구도 실측

권한이 없는 실행 환경에서는 30초 후 촬영 0장으로 종료했다. 카메라 권한이 있는 터미널 앱에서 별도 새 실행을 시작해 1920×1080 BGRA 21장을 보관했다. 평가 프레임의 PTS→처리 진단은 20/20, 최소/중앙값/최대 57.273/65.302/75.374ms, 전체 21장 영속 저장 최대 14.278ms, 보고된 누락은 0장이었다. 처리 진단은 통과했지만 전날과 구도·실행 환경이 달라 개선율로 비교하지 않는다. 광학 노출 시각·USB 전송 경로·의미 기반 대상 물체 앵커는 여전히 미검증이며 실물 학습 적격 전이는 0건이다.

이어 영상·제어기 응답 보관 도구로 한 번 더 유한 관측했다. 4.089초에 GET 14회와 영상 21장을 기록했고 원본 감사가 통과했다. PTS→처리 진단 20/20, 최소/중앙값/최대 58.914/62.728/66.409ms, 영속 저장 최대 16.730ms, 보고된 누락 0장이었다. 여섯 M4 값은 모두 219.81°였으나 보고 나이 9–13ms에 요청 왕복 시간을 더한 값은 55.051–175.123ms로 **20ms 기준 0/6**이었다. 전후 IDLE·모터 다섯 개 OFF, 같은 부팅 ID·출력 이력을 확인했다. ARM·모터 명령은 보내지 않았다. 관측 보관 성공이며, 전체 팔 정착·광학 동기화·행동 전이 적격을 입증한 결과는 아니다.

## HTTP 지연 분리와 같은 Mac 시계 연결

```sh
# 촬영 없이 최대 14 GET: 전후 상태 확인 + curl/direct 각 세 번 비교
python3 tools/probe_controller_latency.py --controller-url 'http://<controller-host>' --output '.local/latency/<new-run>'
# 새 촬영 한 번. 직접 HTTP와 시계 연결은 각각 명시적으로 선택한다.
python3 tools/probe_mac_controller.py --direct-http --clock-bridge --controller-url 'http://<controller-host>' --helper .local/bin/mac-camera-probe --device-id '<Continuity Camera ID>' --view-id '<new-view-id>' --output '.local/observation/<new-run>'
```

직접 HTTP는 매 요청 새 연결을 만들고 닫으며 연결·전송·헤더·본문 구간을 기록한다. 주 스레드의 전체 800ms 기한을 사용하며 기존 타이머가 있으면 거부한다. 응답은 64KiB까지, 재시도·리다이렉트는 없고 잘린 본문과 실패한 요청도 분모와 원본에 남긴다. 지연 비교는 최대 12초이며 오류 시 다음 요청을 보내지 않는다. 비교 요약은 정수 센서 나이의 1ms 양자화 여유를 포함한다.

`--clock-bridge`는 같은 Mac 부팅에서 CoreMedia host clock과 Python `monotonic`이 모두 `mach_absolute_time`을 사용하는지 확인한다. 촬영 전후 각 여덟 호출의 앞뒤 시각으로 변환 구간을 계산하고, 1µs 반올림 여유를 더한다. 변환은 두 계측 사이 최대 50초에만 유효하다. 원래 시계·PTS·응답은 유지하고, 별도 `clock/link.json`에 21개 PTS와 가장 가까운 M4 조회의 **사후** 구간 거리를 기록한다. 감사는 저장된 원본에서 이를 재계산한다.

M4 `ageMs`는 펌웨어의 센서 갱신 시작 표식(ADC 진단 전에 읽은 시각)으로부터의 경과 시간이다. HTTP 시작·수신 구간과 정수 나이 오차를 사용해 이 표식을 호스트 시계 구간으로 제한할 수 있지만 AS5600 내부 물리 샘플 시각은 확인되지 않는다. `presentationClockLinked=true`는 PTS 시계 연결만 뜻한다. `postHocAssociation=true`, `physicalSampleAlignmentVerified=false`이며 광학 노출·인과적 학습 쌍·실물 학습 적격으로 승격하지 않는다.

2026-10-17 지연 비교에서 Mac은 다섯 번째 요청인 첫 curl 조회가 800ms 기한을 초과해 중단했다(비교 1회 시도, 유효 0회). Pi의 별도 14 GET 실행은 완료했지만 curl 왕복 67.499–358.903ms, 직접 HTTP 35.646–53.749ms로 각 세 번 모두 20ms 센서 나이 기준에 미달했다. 실행 호스트·시점이 달라 성능 개선율을 주장하지 않는다.

이어 같은 Mac에서 시계 연결을 켠 14 GET·21프레임 관측과 원본 감사가 통과했다. 시계 변환 구간은 −1.083~+1.125µs, 영상 PTS→처리 진단은 20/20(최소/중앙값/최대 62.074/64.780/71.482ms), 영속 저장 최대 11.451ms였다. M4 보고 나이+왕복 시간은 50.358–286.661ms로 20ms 기준 0/6, PTS와 폴링 표식의 구간 거리 상한도 20ms 이내 0/21이었다. IDLE·다섯 모터 OFF와 전후 부팅·출력 이력 불변을 확인했고 ARM·모터 명령은 0회였다. 시계 연결은 검증했지만 M4 수집 지연과 광학·물리 샘플 정합성은 해결되지 않았다.

### STA 절전 해제 후 확인

제어기 STA 연결·재연결에서 모뎀 절전을 해제하고 `/status`에 드라이버의 실제 절전 상태를 노출했다. 적용·조회 실패는 `unknown` 또는 실제 남은 모드로 보고하며 센서 나이 검사 기준을 완화하지 않는다. 한 차례 업로드 후 유한 조회에서 `stationPowerSave=none`을 확인했지만 직접 HTTP 왕복 36.995–49.389ms, 정수 나이 여유를 포함한 M4 진단 47.995–60.389ms로 20ms 기준은 0/3이었다(curl도 0/3). 절전 해제만으로 수집 지연을 해결했다는 결과는 아니다.

이후 14 GET·21프레임 관측과 원본 감사도 완료했다. PTS→처리 진단 20/20(60.148/64.856/69.428ms), 영속 저장 최대 16.099ms, M4 보고 나이+왕복 시간 49.077–129.992ms로 20ms 기준 0/6이었다. PTS와 폴링 표식의 사후 구간 거리 상한은 2/21이 20ms 이내였지만 광학·물리 샘플 정합성은 여전히 미검증이다. 관측 전후 부팅 ID·출력 이력 불변, IDLE·다섯 모터 OFF를 확인했다. 펌웨어 업로드로 부팅이 바뀐 앞선 실행과는 별도 세션이며, 이전 기록은 보존한다.

## 유선 M4 지연 진단

HTTP 왕복 자체가 20ms를 넘는 경우를 분리하기 위해, 명시적으로 선택한 CP2102N USB 포트에서 센서 상태만 읽는 진단을 제공한다. Python 실행 환경에 `pyserial`이 필요하며, `M4S1` 응답을 지원하는 펌웨어가 필요하다.

```sh
python3 tools/probe_serial_m4.py --controller-url 'http://<controller-host>' --port '<explicit-serial-port>' --usb-serial '<expected-USB-serial-number>' --output '.local/serial-m4/<new-run>'
python3 tools/probe_serial_m4.py --audit '.local/serial-m4/<saved-run>'
```

전후 HTTP 네 번씩과 유선 요청 여섯 번으로 제한하며 세션 12초, 유선 요청 800ms, 저장 250ms를 적용한다. USB VID/PID와 일련번호를 확인하고 DTR/RTS를 열기 전에 false로 설정한다. 리셋·자동 재시도·이전 경로 재개·입력 버퍼 삭제는 없다. 운영체제나 드라이버가 포트 열기 때 리셋한다면 응답의 부팅 ID 불일치로 중단한다.

요청은 `RS(0x1e) + 소문자 16진수 nonce 8자리 + LF`의 전용 프레임이다. RS가 기존 미완성 명령을 폐기하고, 잘못된 프레임도 ARM·모터 명령 파서로 넘기지 않는다. 한 루프에 응답 하나만 생성하며 스트리밍 모드를 켜지 않는다. 73바이트 `M4S1` 응답은 nonce·부팅 ID·AS5600 원시값·갱신 시작/보고 `millis`·센서 준비/IDLE/OFF 플래그를 포함한다. 센서를 강제로 갱신하거나 주기를 바꾸지 않는다.

호스트는 원래 바이트·요청/수신 시각을 저장하고 부팅·nonce·플래그·연속 표본 및 보고 시각 증가를 검사한다. 시작·마지막 각각 200ms의 바이트를 보관하며, 마지막 중복·부분 응답은 거부한다. 수신 중 취소(Ctrl-C 또는 SIGTERM)하면 이미 받은 부분 바이트와 해당 시도 영수증을 보존하고, 포트를 닫고 실패 결과를 봉인한 뒤 종료 코드 130을 반환한다. 추가 요청이나 자동 재시도는 없다. 요청 왕복+보고 나이+1ms 양자화 여유로 20ms 진단을 계산한다. 호스트 시계 구간은 **갱신 시작 표식(ADC 진단 전)**이며 광학 노출이나 AS5600 내부 물리 변환 시각이 아니다. 원시값의 각도 환산은 현재 장착 오프셋 −24.35°를 사용한다. 전후 부팅·출력 이력 불변을 검사하고 모든 학습·구동 적격 플래그는 false로 유지한다.

일부 드라이버는 DTR/RTS 설정과 무관하게 포트 개방 시 제어기를 재부팅한다. 첫 실측은 이 경우로, 원래 부팅의 baseline을 유지한 기본 모드가 첫 요청에서 시간 초과로 중단했다. 성공 표본 0개, 유선 요청 1회이며 부팅 로그와 실패 원본을 보존했다.

그런 환경의 **수집 전 초기화**를 명시적으로 선택할 때만 `--initialize-port`를 추가한다. 포트 개방 전 HTTP 네 번으로 IDLE·OFF·센서·빈 큐·비활성 제한 행동을 검사하고, 한 번 연 포트에서 20초·최대 64KiB의 시작 로그를 보존한다. 두 번 이상의 부팅 로그는 거부한다. 이후 새 HTTP 네 번을 baseline으로 삼고 센서 여섯 번·완료 HTTP 네 번을 수행한다(총 HTTP 12회, 세션 32초). 같은 부팅이면 개방 전후 출력 이력이 같아야 하며, 부팅이 바뀌었으면 새 출력 이력에 누락이 없고 다섯 모터 모두 0 출력만 있어야 한다. 초기화 중 부팅 변경은 별도 필드에 기록하고 이전 원본은 유지한다. **새 baseline 이후**에는 여전히 부팅·출력 변화 시 중단한다. 실패한 시험을 자동 재개하거나 이전 구동을 재전송하지 않는다.

초기화 옵션을 선택한 별도 실측은 21.164초, HTTP 12회·유선 6회로 완료했고 원본 감사가 통과했다. 초기화 중 부팅 변경을 기록했으며 새 baseline 이후 부팅·출력 이력은 유지됐다. 유선 왕복은 12.666–19.947ms, 보고 나이+왕복+1ms는 21.666–36.993ms로 20ms 기준 **0/6**이었다. 센서 갱신 주기가 20ms인 캐시 응답과 전송 지연이 합쳐진 결과이며, USB 연결만으로 기준을 해결한 것으로 해석하지 않는다. 모터 요청은 0회이고 물리 샘플·광학 시각·학습 적격은 여전히 미검증이다.

### 다음 정상 갱신값과 내부 대기 구분

`--fresh-sample`은 `RS + 2 + nonce 8자리 + LF`를 보내며 `M4S2` 응답을 요구한다. S1 기본 모드는 그대로다. 펌웨어는 IDLE·OFF·센서 준비 상태에서 요청 하나만 대기시키고, 요청 수신 표식보다 뒤인 **다음 정상 주기 갱신** 뒤 한 번 응답한다. 대기 중 추가 진단 요청은 대기를 교체하지 않는다. 150ms 초과나 상태 변화 시 응답 없이 취소하며, 기존 명령 입력·안전 루프는 계속 처리한다. 새 센서 읽기·주기 변경·모터 명령·스트리밍은 없다.

82바이트 응답은 요청 수신 `millis`를 추가한다. 호스트는 수신→갱신→보고의 순서·150ms 한도·uint32 순환을 검증한다. 전체 왕복은 그대로 보존하며, 센서 나이 진단은 `왕복 − 내부 대기 하한 + 보고 나이 상한`으로 별도 계산한다. 각 MCU 구간에는 정수 양자화 1ms와 최대 150ms 구간의 시계 속도 오차를 위한 추가 1ms를 적용한다. 이는 **명시한 진단 가정**이며 MCU 시계 속도를 실측 보정한 결과가 아니다(`mcuClockRateCalibrated=false`). 뺄 대기 하한이 호스트 왕복보다 크면 거부한다. 전송 시간이나 물리 샘플 나이를 직접 측정했다고 주장하지 않는다.

첫 S2 실측은 HTTP 12회·유선 6회와 원본 감사가 완료됐다. 전체 왕복 29.203–74.986ms, 내부 대기 17–47ms, 센서 보고 나이 4–5ms였으며 위 가정의 나이 상한은 20.203–36.986ms로 **20ms 기준 0/6**이었다. 다음 정상 갱신을 기다리므로 전체 왕복을 S1의 캐시 조회와 같은 지표로 비교하지 않는다. 이어 호스트 수신은 준비된 바이트를 한 번에 읽도록 구현했다. 최대 원본 크기·전체 기한을 유지하고 묶음에 들어온 중복·부분 응답도 거절하며, 바이트당 시스템 호출 비용을 줄이는 변경의 효과는 별도 실행으로 평가한다.

묶음 수신 적용 후 별도 실측도 HTTP 12회·유선 6회와 원본 감사를 통과했다. 전체 왕복 21.145–45.900ms, 내부 대기 8–24ms, 보고 나이 4–5ms, 진단 나이 상한 20.145–34.900ms로 **20ms 기준 0/6**이었다. 단일 실행의 6개 표본으로 수신 방식의 성능 개선을 입증하지 못했다. 새 baseline 이후 부팅·출력 이력 불변, IDLE·다섯 모터 OFF를 확인했고 모터 요청은 0회였다. 다음 수집 적격 판정에는 전송 경로 지연과 MCU 시계 속도·물리 샘플 시각의 계측이 더 필요하다. 이 진단 결과를 기존 `DeviceCaptureSession`의 검증된 센서 시각으로 자동 변환하는 경로는 제공하지 않는다.

### 호스트 전송 경계 계측

```sh
python3 tools/probe_serial_m4.py --initialize-port --fresh-sample --transport-trace --controller-url 'http://<controller-host>' --port '<explicit-serial-port>' --usb-serial '<expected-USB-serial-number>' --output '.local/serial-m4/<new-traced-run>'
```

`--transport-trace`는 펌웨어·baud·센서 주기를 바꾸지 않고 호스트의 쓰기, 버퍼 조회, 각 읽기, 파싱 작업 전후 단조 시각을 영수증에 추가한다. 각 읽기의 요청/반환 바이트 수·원본 offset·조각 해시를 함께 보존한다. 빈 읽기도 포함해 요청당 최대 256회이며 초과하면 실패로 남기고 후속 요청을 보내지 않는다. 계측은 메모리에 모은 뒤 기존 영수증 저장에서 함께 영속화하며, 시간 조회와 기록에 드는 비용도 실행에 포함된다.

감사는 성공뿐 아니라 실패·취소 시도에도 계측 모드 일치, 시간 순서, 원본 바이트 합계·offset·조각 해시, 중단 지점과 호출 상한을 검사한다. 감사 결과의 `transportTraceSummaries`는 첫 비어 있지 않은 읽기 완료, 응답을 포함한 마지막 읽기 완료, 파싱 시간을 구분한다. 첫 읽기에는 DEBUG 로그가 들어올 수도 있다. 이 시각들은 **Python이 관측한 작업 경계**이며 UART 첫 바이트, USB 도착, 광학 노출 또는 센서 변환 시각이 아니다. 쓰기 반환도 물리 전송 완료를 뜻하지 않는다. 읽기 구간에는 원본 바이트를 메모리에 붙이는 작업도 포함되고, 단계 사이에는 조건 검사·해시·스케줄링 등이 남는다. 따라서 전체 왕복에서 기록된 단계 시간을 뺀 나머지를 USB 지연으로 특정할 수 없다. 기존 `receivedMonotonic`과 20ms 진단 계산은 유지한다.

앞선 S2 묶음 수신 실행의 첫 원본에는 정상 응답 전 DEBUG 로그 87바이트가 있었고 나머지 다섯 개는 정상 응답 82바이트였다. 이상적인 115200/8N1 직렬화 시간은 82바이트에 7.118ms지만, 실제 UART·USB·호스트 구간의 측정값은 아니다. 이 차이와 수신 경계 계측으로 원인을 좁히되 여섯 표본만으로 성능 개선이나 특정 계층의 책임을 단정하지 않는다.

2026-10-18 계측 실행은 HTTP 12회·S2 6회와 원본 감사를 통과했으며, 나이 상한은 20.970–30.327ms로 20ms 기준 0/6이었다. 쓰기 작업은 0.097–0.167ms, 파싱 작업은 0.049–0.116ms였다. 첫 원본에는 선행 로그 103바이트가 있었고, 나머지 다섯 응답의 비어 있지 않은 read 반환 크기는 모두 `[1,63,1,17]`이었다. 첫 반환부터 마지막 반환까지 3.312–3.598ms였으나, read 요청 크기도 같은 값이므로 USB 패킷 경계를 측정한 결과로 볼 수 없다. 새 baseline 이후 출력·부팅 불변과 모터 요청 0회를 확인했다. 이 표본에서는 파싱이 수ms 지연의 주된 원인으로 보이지 않으며, 정보가 같은 짧은 응답을 별도 시험할 근거로만 사용한다.

### 같은 정보를 보존하는 축약 응답

```sh
python3 tools/probe_serial_m4.py --initialize-port --compact-sample --transport-trace --controller-url 'http://<controller-host>' --port '<explicit-serial-port>' --usb-serial '<expected-USB-serial-number>' --output '.local/serial-m4/<new-compact-run>'
```

`--compact-sample`은 다음 정상 갱신을 기다리는 S3를 명시적으로 선택한다. 요청은 `RS + 3 + nonce 8자리 + LF`, 응답은 `M4S3 `·Base64 52문자·LF의 58바이트다. 39바이트 payload는 빅엔디언 nonce 4바이트, 전체 부팅 ID 16바이트, 원시값 2바이트, 갱신·보고·요청 수신 표식 각 4바이트, 플래그 1바이트, 앞선 35바이트의 CRC32/IEEE 4바이트다. CRC는 손상 검출이며 인증 수단은 아니다. 길이·정규 Base64·CRC·식별자·시간 순서 중 하나라도 맞지 않으면 실패로 보존하고 다른 형식으로 재시도하지 않는다.

S1·S2는 유지하며, S3도 같은 센서 주기·150ms 대기 한도·상태 검사·시계 오차 가정·20ms 기준을 사용한다. 82→58바이트의 이상적인 115200/8N1 직렬화 차이는 2.083ms지만 실제 지연 감소나 단일 USB 패킷 수신을 보장하지 않는다. 전체 부팅 ID와 시각을 줄이거나 물리 샘플·광학 노출의 검증 상태를 바꾸지 않는다.

첫 S3 실행은 2회 시도·유효 1개 뒤 중단됐다. 첫 원본은 선행 경고·DEBUG 로그 185바이트와 정상 58바이트 응답을 포함했고 나이 상한은 34.825ms로 20ms 기준을 충족하지 못했다. 두 번째 원본은 정상 응답 뒤 `[WARN]` 6바이트가 함께 읽혀 불완전한 뒤쪽 줄로 거부됐다. 전체 여섯 표본 시험을 완료한 결과가 아니며 원본 실패·분모를 유지한다. 원본 감사는 통과했고 별도 읽기 전용 후속 확인에서 baseline 이후 부팅·출력 불변, IDLE·다섯 모터 OFF·센서 준비를 확인했다. 자동 재시도나 모터 명령은 없었다. 이후 수집기는 정상 응답 뒤 일부 로그가 같은 read에 섞이면 원본 전체가 LF로 끝날 때까지 기존 800ms·4096바이트·계측 시 256회 읽기 한도 안에서 기다리도록 수정했다. 요청을 다시 보내거나 원본을 잘라내지 않으며, 종료되지 않는 로그·부분 응답·중복은 여전히 거부한다. 수신 시각에는 추가 로그를 기다린 시간도 포함하므로 진단 상한을 앞당기지 않는다. STM32 `parse failed` 경고는 별도 통신 이상 관측으로 남으며, 후속 센서 준비 응답이 이를 해결했다는 증거는 아니다.

경계 수정 후 별도 S3 실행은 21.227초·HTTP 12회·유선 6회와 원본 감사를 완료했다. 전체 왕복 28.561–67.929ms, 내부 대기 13–44ms, 보고 나이 4–5ms, 진단 나이 상한 20.559–32.929ms로 **20ms 기준 0/6**이었다. 첫 원본에는 선행 로그 146바이트가 있었고 나머지 다섯 원본은 각각 정상 응답 58바이트였다. 다섯 응답의 비어 있지 않은 read 크기는 `[1,57]`, 첫 반환→마지막 반환 간격은 0.043–0.134ms였다. 후반부 읽기 간격이 짧게 관측됐지만 서로 다른 실행 여섯 표본으로 전체 수집 성능 개선을 입증하지 못하며, 남은 시간을 USB 지연으로 특정할 수 없다. 새 baseline 이후 부팅·출력 이력 불변, IDLE·다섯 모터 OFF를 확인했다. 모터 요청 0회, 물리 시각·학습 적격은 여전히 미검증이다.

코드·과거 원본 분석에서 STM32 bridge의 Serial2 입력 오류가 `DebugLog`를 통해 USB Serial 출력에 경고를 쓰는 경로를 확인했다. 선택된 센서 공급원의 정상 상태와 다른 UART의 오류는 구분해야 한다. 경고는 S3 도입 전에도 있었으며, 로그 문자열은 NUL에서 잘릴 수 있어 실제 잘못된 입력 전체를 복원하지 못한다. 배선·노이즈 등 원인은 확정되지 않았고, 새 Serial 로그를 늘리는 대신 UART별 제한된 진단 카운터와 원본 바이트 보존이 후속 계측 대상이다.

### 펌웨어 내부 구간 계측

```sh
python3 tools/probe_serial_m4.py --initialize-port --compact-sample --transport-trace --firmware-timing --controller-url 'http://<controller-host>' --port '<explicit-serial-port>' --usb-serial '<expected-USB-serial-number>' --output '.local/serial-m4/<new-stage-run>'
```

S2·S3 요청은 최근 8건의 nonce별 처리 기록을 RAM에 남긴다. 읽기 전용 `GET /m4_diagnostics`는 이 기록과 부팅 ID·연속 번호·이전 기록 덮어쓰기 수를 조회하며, 기록을 지우거나 센서 갱신·출력을 유발하지 않는다. 추가 Serial 로그나 응답 필드는 없다. 호스트의 `--firmware-timing`은 S3에서만 사용하며 기존 유한 수집 전후에 조회를 한 번씩 추가한다(일반 HTTP 합계 10회, 포트 초기화 시 14회). 기존 800ms 요청·12/32초 세션·250ms 저장 한도와 센서 여섯 번을 유지한다. 같은 부팅에서 여섯 nonce와 연속 번호·응답 표식·원시값·58바이트 쓰기를 대조한다. 기존 기록의 정상 덮어쓰기는 별도 집계하고 새 요청 누락이나 다른 요청의 개입은 거부한다.

`esp_timer_since_boot_us` 기록은 요청 파싱, 센서 갱신 함수 진입, 조건부 ADC 단계 통과, I2C 폴링 시작, 각도 읽기 함수 전후, 폴링 완료, 응답 쓰기 호출 전후를 구분한다. `adcSampled`는 해당 갱신에서 실제 ADC 호출 여부이며, `pollAttempts`와 `latestPollOnly`는 여러 정상 주기를 기다렸다면 마지막 폴링 단계만 보존한다는 뜻이다. 각도 읽기 구간은 레지스터 접근·I2C 전송·바이트 복사를 포함한다. 폴링 완료에는 기존 보조 레지스터 조회와 로그 경로가 포함될 수 있다. 루프 시작 사이의 간격은 전체 루프 간격이며 CPU 스케줄러 지연만을 뜻하지 않는다.

이 시각은 AS5600 내부 변환·UART 첫 수신·USB 도착·물리 전송 완료가 아니다. MCU 시계 속도는 보정되지 않았으며, 호스트 시각과 절대값을 직접 빼지 않는다. 요청 파싱 이전의 UART 대기는 여전히 미계측이다. 원본 S3 표식과 20ms 나이 계산은 유지하고 단계 계측 결과로 학습 적격을 부여하지 않는다.

2026-10-18 내부 계측의 첫 유한 실행은 센서 6회·상태 HTTP 12회·진단 HTTP 2회와 원본 감사를 통과했다. 나이 상한은 19.318–27.423ms로 20ms 기준 **4/6**이었다. 여섯 요청 모두 정상 폴링 한 번·ADC 호출·각도 읽기 성공·58바이트 쓰기를 기록했다. 요청 파싱→센서 갱신 진입 2.662–19.794ms에는 20ms 정상 폴링의 위상 대기가 포함된다. ADC 단계 0.674–0.897ms, 각도 읽기 함수 0.720–0.743ms, 응답 쓰기 호출 0.133–0.188ms를 관측했다. 마지막 값은 UART 전송 완료가 아니며, 한 번의 여섯 표본으로 안정적인 20ms 충족이나 성능 개선을 입증하지 못한다. 새 baseline 이후 부팅·출력 이력 불변, IDLE·다섯 모터 OFF를 확인했고 모터 명령은 0회였다.

직접 HTTP·curl 수신 중 취소해도 관측한 부분 본문·요청 시도를 저장한 뒤 중단하도록 공용 수집 경로를 보강했다. curl은 같은 요청의 정리만 수행하고 TERM·KILL 이후 대기를 각각 0.2초로 제한한다. 취소 응답을 성공으로 처리하거나 다음 요청을 보내지 않으며, USB와 카메라 자원 정리 및 가능한 실패 봉인을 수행한다. 저장 자체가 실패해 원본이 없으면 무결성 감사도 통과하지 못한다.

### USB 센서·영상 동일 세션 시계 연결

```sh
python3 tools/probe_usb_camera.py --initialize-port --controller-url 'http://<controller-host>' --port '<explicit-serial-port>' --usb-serial '<expected-USB-serial-number>' --helper '<native-camera-helper>' --device-id '<explicit-camera-ID>' --view-id '<new-view-ID>' --output '.local/usb-camera/<new-run>'
python3 tools/probe_usb_camera.py --audit '.local/usb-camera/<existing-run>'
```

한 생산자가 촬영 전에 새 세션 ID·호스트 시계 ID를 생성한다. 공통 세션 ID는 영상 원본과 여섯 S3 응답에 기록하고, 호스트 시계 ID는 USB 응답과 시계 변환 자료에 기록한다. 영상 원본은 CoreMedia 호스트 시계 영역을 표시하며 이 변환 자료를 통해 연결된다. 같은 Mac 부팅에서 촬영 전후의 CoreMedia 호스트 시계↔Python monotonic 변환 구간을 측정하고, 21개 PTS·callback·처리·저장 시각과 여섯 요청·수신·폴링 표식 구간이 카메라 프로세스 구간 안에 있는지 검사한다. MCU 부팅 ID·nonce·원시값은 펌웨어 RAM 단계 기록과 다시 대조한다. 과거 원본에 새 세션 이름을 붙여 같은 시각의 자료로 취급하지 않는다.

수집은 영상 21프레임·S3 6회·상태 HTTP 8회·진단 HTTP 2회로 제한된다. `--initialize-port`는 포트 개방 후 20초 시작 로그 수집과 새 baseline을 사용하므로 상태 HTTP는 12회, 전체 한도는 80초다. 옵션이 없으면 전체 60초다. 카메라 프로세스는 최대 47초, 시계 연결 구간은 최대 50초, 정리 유예는 최대 4초이며 재시도는 없다. 초기화 중 부팅이 바뀌면 새 부팅에서 다섯 모터의 완전한 OFF 이력이 필요하고, baseline 이후 부팅·출력 이력 변경은 거부한다. 카메라 종료·부분 응답·취소·저장 실패는 가능한 원본을 보존하고 자원을 정리한다. 감사는 저장된 원본·해시·순서·세션 식별자를 다시 계산한다.

2026-10-18 첫 통합 실행은 초기화 포함 23.324초에 센서 6회·영상 21프레임·상태 HTTP 12회·진단 HTTP 2회를 마쳤고 원본 감사가 통과했다. 시계 변환 오프셋 구간은 약 −1.125~+1.125µs였다. 평가 영상의 PTS→처리 진단은 56.743–70.787ms로 100ms 기준 **20/20**, 원본 영속 저장은 10.838–17.093ms로 250ms 기준 **21/21**이었다. M4 나이 상한은 19.030–28.920ms로 20ms 기준 **2/6**이며, 앞선 센서 단독 실행의 4/6과 달라 안정적 충족은 아직 입증하지 못했다.

각 영상 PTS 구간과 가장 가까운 센서 폴링 표식 구간의 최대 거리를 사후 계산했을 때 20ms 이내는 **6/21 프레임**이었다. 이는 M4 응답 나이 2/6과 서로 다른 분모·지표다. 첫 프레임을 저장한 뒤 센서 여섯 번만 읽는 관측이므로 모든 영상에 센서가 대응한다고 보장하지 않는다. 이 연결은 물리적 동시성·인과적인 행동 전이·학습용 페어가 아니다. 카메라 케이블 연결만으로 영상 전송 경로가 USB라고 확정하지 않는다.

새 baseline 이후 IDLE·다섯 모터 OFF·출력 이력 불변을 확인했으며 모터 명령은 0회였다. 광학 노출 시각, AS5600 물리 변환 시각, 대상 물체 의미 앵커와 행동 전후 연결은 미검증이다. 영상 100ms·앵커 15초·원본 저장 250ms 기준을 유지하며 실물 학습 적격 전이는 **0건**이다.

## 고정 오프라인 검출 평가

```sh
python3 tools/evaluate_mac_camera_detection.py --capture-dir 'datasets/mac_camera/<saved-run>' --model .local/models/yolov5s.onnx --labels config/coco80.labels --output '.local/detector-evaluation/<new-run>'
```

입력·모델·라벨·코드 해시를 고정하고 CPU 작업자 하나, 60초 기한·2초 종료 유예, 준비 한 번·21평가를 실행한다. 설정은 YOLOv5s ONNX 입력640, cup, confidence0.20, NMS0.45, 가장 큰 대상, 별칭 없음이다. 새 촬영·학습·파라미터 탐색은 없다.

첫 구도 21장에서 컵 검출은 0/21이었다. 검출기 호출 중앙값 268.809ms, 입력 준비 포함 전체 중앙값 320.146ms였다. 정답 박스가 없어 정확도 평가가 아니며, 재생 시간은 실시간 촬영→검출 지연이 아니다. 새 구도의 검출 성능은 평가하지 않았다. 원본 장면과 세션 기록은 비공개로 보관한다.

## 화면 표식 오프라인 검증

추가 계측 장비 없이 화면의 새 표식으로 노출 구간을 제한하는 조건과 ESP32-CAM 처리 경로의 한계는 [화면 표식의 오프라인 시간 검증](optical-challenge-offline.md)에 정리했다. 합성 픽셀·시간 모델만 검사하며 실제 노출 상한, 촬영 경로 또는 학습 적격을 인증하지 않는다.
