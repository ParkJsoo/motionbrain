# M4 장치 목표 가드

[운영 안내](../OPERATIONS.md) · [문서 색인](README.md)

호스트가 HTTP로 각도를 관측하고 STOP을 요청하는 경로와 별도로, 장치의 main loop에서 목표·센서·기한을 검사하고 드라이버를 OFF하는 경로다. 기본 펌웨어에서는 비활성이다. **소프트웨어 연결과 실물 정지 검증은 다르다.** 전용 펌웨어 업로드와 새 부팅에서 5모터 OFF·정책 capability 읽기 확인을 마쳤다. 물리 정지거리와 모델 기반 전체 과업 완주는 아직 검증하지 않았다.

## 실행 계약

- 전용 `/sequence` 동작 `add_m4_guarded`·`run_m4_guarded`를 사용한다. 일반 시퀀스 큐와 분리하며, 일반 큐가 비어 있고 모든 출력이 OFF여야 한다. GET 응답의 `m4GoalGuard`에 capability와 실행 레코드를 제공한다.
- 요청에는 부팅 ID·nonce·scope·정책 해시·시작각·목표각을 묶는다. nonce는 부팅 내 고정 용량으로 보존한다. 사용한 nonce나 OFF가 확인되지 않은 종료 상태에서는 새 실행을 허용하지 않는다. 최초 OFF 확인은 뒤의 확인으로 덮어쓰지 않는다.
- RUN 수락 응답 이후 main loop에서 현재 센서·안전 상태를 확인하고 실행한다. 출력에는 기존 램프를 사용하며, 정지 결정에는 직접 hard OFF를 사용한다. 일반 출력 경로가 가드 실행을 덮어쓰지 못하도록 드라이버 소유권을 검사한다.
- 각도는 기존 상태 API와 같은 AS5600 장착 보정 좌표다. 센서 원시각이나 다른 촬영·자세 계약으로 바꿔 끼우지 않는다.
- 기존 v1/v2 정책은 UP 50%·DOWN 35%, 요청 기한 1,200ms, 관측 변화 한도 0.9°를 고정한다. 시작·목표·전역 범위도 기존 명시 정책을 유지한다. 임의 현재 자세에 적용하는 범용 복귀 명령이 아니다.

## 현재 자세에 결합하는 정책

기존 v1은 탁상 기준 197.22°·UP 목표 197.85°를 그대로 유지한다. 별도 v2 정책은 `current_table_device_guard_policy(table_reference_deg)`로 현재 확인한 탁상 기준각을 명시한다. 기준각은 192.29~197.39°이고, UP은 그 기준각에서 +0.63°를 목표로 한다. DOWN은 기준각보다 0.1° 초과·0.9° 이하인 상태에서 기준각을 목표로 한다. 시작 직전 실제 센서 상태도 검사하므로 시작 오차 허용치를 이용해 이 범위를 넘길 수 없다.

예를 들어 새로 확인한 기준각이 194.32°이면 UP 목표는 194.95°다. 과거 계약에 맞추기 위해 먼저 197.22°로 이동할 필요는 없다. 이 숫자는 승인된 움직임이나 현재 등록을 뜻하지 않으며, 매 실행의 현재 영상·부팅·출력 cursor·시작각·현장 여유 확인에 결합해야 한다.

v2는 별도 정책 해시와 `tableReferenceDeg`를 요청·장치 레코드에 포함한다. 지원 정책 목록에 v2가 없는 펌웨어에는 RUN을 보내지 않는다. 원본 감사·모델·factory에서도 동일 정책과 장면 계약을 요구하므로 v1 자료나 다른 카메라 boot·자세의 자료를 재표시하여 섞을 수 없다. 기존 FSM과 0.9° 국소 한도·전역 범위·출력·기한은 유지한다.

## 명시한 목표를 선택하는 v3 UP 정책

`finite_goal_device_guard_policy(goal_angle_deg)`는 시작 기준 +0.63°를 강제하지
않는 별도 UP 전용 정책이다. 모델이 비교한 목표각을 실행 scope와 정책 해시에
고정한다. UP 50%·최대 1,200ms는 유지하며 DOWN은 지원하지 않는다. v1/v2의
탁상 기준이나 DOWN 목표를 상속하지 않고, 기존 paired-cycle factory에서도 이
정책을 명시적으로 거절한다. 별도 개발 목표 실행기를 통해서만 연결한다.

요청·실제 시작각에서 목표까지의 차이는 0.1~2.5°이며, 목표는 기존 전역 범위
192.29~198.29°의 양 끝에서 0.5° 안쪽이어야 한다. 시작각 기준 관측 변화 한도는
3°다. 이 수치는 개발 실행 범위이며 실측 기구 끝점이나 물리 정지거리 보장이
아니다. 센서 지연·OFF 이후 이동은 별도로 관측한다. 기존 상태기계·nonce·센서
이상·기한·STOP·드라이버 hard OFF 경로를 재사용한다.

v3 capability가 없는 펌웨어에는 해당 RUN을 보내지 않는다. 기본·전용 빌드와
모의 장치 검증은 실제 배포·관측·구동 검증과 구분한다. 여러 목표를 순차 비교하는
개발 실행에서도 각 목표는 한 번만 소비하며, 실패·unknown 뒤 새 ID로 대체하거나
자동 재전송하지 않는다. 정상 종료 후의 새 영상에 따른 다른 목표 선택은 별도로
기록한다. 센서 목표 도달과 영상의 물체 이탈·보유 성공은 같은 판정이 아니다.

## 통신과 정지

가드 운전 중 일반 HTTP 처리를 지연해 호스트 조회가 장치 제어 검사를 막지 않도록 한다. 따라서 **HTTP STOP 응답을 즉시 정지 채널로 간주하면 안 된다.** 운전 중에는 별도 직렬 `!` 취소와 기존 안전 입력을 처리하며, 상태·센서·출력 소유권 이상도 종료 조건으로 검사한다. 종료 후에는 남은 직렬 입력을 폐기하고 출력 차단을 유지한다. 입력 정리 뒤 새 명시적 웹 ARM에서만 일반 출력 차단을 해제한다. STOP·큐 정리·무출력 기본 속도 복구는 허용하지만, 이전 직렬·대기 명령으로 재출력하지 않는다.

직렬 `!`는 loop당 최대 64바이트를 소비하는 정지 입력이며 반응시간은 실측하지 않았다. STA 연결 상실은 검사하지만 정상 HTTP 소켓 종료·호스트 중단·네트워크 무응답을 즉시 감지하는 연결 생존 보장은 없다. 이때도 장치의 센서·목표·1,200ms 기한 검사를 사용한다. AP 모드도 원격 클라이언트 생존을 보장하지 않는다.

센서 poll 설정 20ms는 실제 검사 주기나 물리 정지거리를 보장하지 않는다. I2C·UART·다른 loop 작업의 지연이 존재하며, 검사 간격 초과는 다음 검사에서 감지된다. 실행 레코드의 센서 시각·나이, 첫 검사 지연·최대 검사 간격, 정지 결정·OFF 시각을 따로 확인해야 한다. 소프트웨어 OFF 확인도 관성에 의한 이동 종료나 물체 보유를 증명하지 않는다.

## 호스트와 자료 연결

호스트는 capability·정책·nonce·queue readback을 검사한 뒤 RUN을 한 번만 요청한다. 운전 중 HTTP 각도 조회를 하지 않고, 유한 대기 후 terminal 레코드를 검증한다. RUN 응답 유실·terminal 이상·관측 실패는 기존 실패 및 unknown 처리로 남기며 자동 재전송하지 않는다.

수집 actor, 원본 HTTP·출력 감사, 모델의 실행 정책과 전체 과업 factory는 별도 device-guard schema를 사용한다. 기존 short/effective 자료를 새 정책 자료로 자동 전환하지 않는다. 기한 종료는 목표 도달이나 들기 성공이 아니며, 영상의 탁상 이탈·보유·내려놓기·해제 판정은 별도로 필요하다. 기존 실패 원장과 pending 차단은 이 기능을 구현하거나 펌웨어를 재부팅했다는 이유로 해소되지 않는다.

## 재부팅 후 실패 차단 해소

`learning/m4_failed_run_recovery.py`는 M4 actor의 실패·unknown·pending 원본을 보존하고, 다른 부팅에서 현재 5OFF·빈 큐·미사용 가드를 GET으로 확인한 뒤 해당 실행 차단 행의 phase만 조건부로 갱신하는 별도 경로다. 기존 원본과 DB 결과를 성공으로 바꾸거나 실패한 RUN을 재전송하지 않는다. 이 확인은 과거 출력 결과나 물리 정지거리의 증명이 아니다.

기존 원장·원본의 일치와 다른 미해결 행을 검사하고, 해소 시도는 실행 전에 별도로 소모한다. 현재 확인 실패·자료 변경·동시 갱신은 차단을 유지한다. 구현과 테스트 통과가 실제 원장 갱신을 허용하는 것은 아니며, 해당 실패 행의 현재-OFF 해소 범위를 명시적으로 승인받은 뒤 실행한다. 장치 재부팅이나 펌웨어 업로드만으로 이 절차를 대신하지 않는다.

## 빌드와 배포 경계

```sh
python3 -m unittest tests.test_m4_goal_guard_native tests.test_m4_goal_service_native tests.test_m4_device_guard_transport tests.test_m4_device_guard_integration tests.test_m4_current_table_guard tests.test_m4_finite_goal_guard
pio run -e esp32dev
pio run -e esp32dev_m4_goal_guard
```

`esp32dev_m4_goal_guard`는 명시적으로 선택하는 전용 빌드다. 기본 환경은 `esp32dev`를 유지하며 부팅 시 자동 동작하지 않는다. 네이티브 검사는 컴파일러가 없으면 건너뛴다. 모의 입력 검사와 빌드 통과는 실제 장치·배선·부하에서의 정지 검증을 대신하지 않는다.

배포 전에는 해당 소스·바이너리, 업로드 대상, 변경되는 정지 채널과 복귀 방법을 확인한다. 업로드 승인과 모터 구동 승인은 구분한다. 실물 실행 전에는 현재 부팅·연결·OFF·센서·두 영상·이동 여유와 미해결 원장 차단을 다시 확인해야 한다. 다른 자세·카메라 boot·좌표계의 자료나 저장된 장치 상태를 현재 조건으로 간주하지 않는다.


### 정지 영상의 밝기 변화와 위치 변화

정지 영상 비교는 기존 NCC 0.995 기준과 평균 회색값 차이 3 이하 경로를 유지한다. NCC는 통과하고 평균 차이만 초과한 경우에 한해 ROI 전체의 회색값 차이 중앙값 하나를 빼는 전역 밝기 오프셋 검사를 추가한다. gain 보정, 영상 이동·회전 정렬, 구역별 밝기 보정은 하지 않는다. 두 ROI에 0·255 포화 픽셀이 없고, 오프셋을 뺀 값도 0~255 범위를 벗어나지 않아야 한다. 보정 후 평균 절대 잔차·잔차 표준편차·4×4 각 구역의 평균 절대 잔차가 각각 3 이하여야 한다. 원래 평균 차이와 오프셋·보정 잔차를 함께 기록한다.

이는 밝기만 달라진 영상을 무조건 재촬영하지 않기 위한 소프트웨어 검사다. 낮은 질감, 실제 위치 변화, 국소 그림자, 포화로 잃은 대비를 복원하거나 접촉·안전을 증명하지 않는다. 별도의 픽셀 계측, 현재 부팅·출력 이력, 원본·구도 결합과 3초 신선도 검사는 그대로 적용하며 과거 거절 기록을 고치지 않는다.
