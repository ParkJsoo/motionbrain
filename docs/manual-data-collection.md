# 관절별 수동 데이터 수집 화면

[운영 안내](../OPERATIONS.md) · [기존 감독 수집](supervised-action-collection.md)

기존 Control Console의 관절·방향 선택 방식을 참고한 Mac 로컬 화면이다. M1~M5 중 한 관절을 선택해 짧은 동작을 요청하고 영상·명령·실제 드라이버 출력·센서 응답을 보존한다. 완료·실패·중단 기록의 프레임과 이력을 다시 확인할 수 있다. 서버 실행과 기록 조회만으로 촬영·구동하지 않는다.

## 실행

저장소 루트에서 촬영기를 빌드한다. 빌드는 카메라를 열지 않는다.

```sh
mkdir -p .local/bin
bash tools/macos/build_action_recorder.sh .local/bin/mac_action_recorder
```

카메라 연결 후 `.local/bin/mac_action_recorder --list`로 장치 식별자를 조회한다. 기존 운영 방식으로 `MOTIONBRAIN_HTTP_TOKEN`을 환경변수에 설정하고 아래 값은 현재 주소·식별자로 바꾼다. 토큰을 명령 인수·문서·기록에 넣지 않는다.

```sh
python3 tools/manual_collection_server.py \
  --controller-url 'http://<현재 ESP32 주소>' \
  --device-id '<카메라 uniqueID>' \
  --helper .local/bin/mac_action_recorder
```

브라우저에서 `http://127.0.0.1:8765`를 연다. 서버는 루프백에서만 수신한다. 기본 저장 경로는 `.local/manual-collection/`이며 `--output-dir`도 저장소 `.local/` 아래만 허용한다. macOS 카메라 권한과 iPhone 연결은 준비되어 있어야 한다.

## 사용

1. 관절·시작 자세·하중 메모를 입력하고 현재 연결·모터 전원·이동 여유를 확인한 뒤 **수집 시작**을 누른다.
2. 저장 중인 최신 영상을 확인하고 방향·요청 출력·시간을 지정해 **한 번 조작**한다. 요청과 정지 확인이 끝나야 다음 동작을 받는다.
3. **완료·저장**으로 종료한다. **수집 중단**은 중단 사유를 보존한다. 다른 관절은 새 수집에서 선택한다.
4. 기록을 선택하고 재생·슬라이더로 프레임과 이력을 확인한다. **전체 이력**은 마지막 영상 뒤 수신한 정지·종료 기록도 표시한다.

첫 버전은 누르는 동안 계속 구동하는 방식이 아니라 기존 `SequencePort`의 유한 단발 요청이다. 기존 방향·출력 상한을 적용하며 M4는 과거 큰 이동 때문에 아래 방향 1회/기록만 허용한다. 다른 관절은 최대 20회/기록이다. 이 상한은 현재 자세의 안전한 이동 거리를 보장하지 않는다.

촬영 예산은 최대 60초·8fps·500프레임이다. 서버 시작이 아닌 **수집 시작 후** 50초를 넘으면 새 동작을 받지 않고 55초부터 종료한다. 준비·통신 시간도 포함되어 실제 촬영은 더 짧을 수 있다. 최대 저장 예산과 2GiB 여유 공간을 요구한다.

## 저장과 시간

형식은 `motionbrain.manual_collection.v1`이며 기존 정착 전후 자료·M2 고정 출력 자료와 자동 혼합하지 않는다.

| 내용 | 파일·의미 |
| --- | --- |
| 설정 | `plan.json`: 관절·자세·카메라 설정·촬영기 해시 |
| 영상 | `native-camera/`: 무손실 프레임·PTS·메타데이터·해시·호스트 시계 대응 |
| 명령 | `command-*-intent.json`, `command-*-result.json`: 전송 전 의도와 결과 |
| 통신·센서 | `http-*` 기록: 요청·원본 응답·오류와 호스트 시작·수신 시각 |
| 종료 | `session.json`: 프레임 색인·이력·종료 상태·출력 정지 확인 |

M4 각도와 공통 센서는 수집 전용 `/collection_status` 응답을 보존한다. 기존 기록의 `/status`도 재생할 수 있다. 센서 없는 관절의 각도를 만들지 않는다. 최근 수신 각도와 오래된 값 여부는 화면에, 전체 센서는 기록 원문에 표시한다.

영상 PTS는 기존 촬영기의 호스트 시계 구간으로 대응한다. HTTP 이력은 호스트 요청·응답 구간이며 출력 `atMs`는 ESP32 부팅 시계다. 정확한 장치 간 시계 동기화나 광학 노출 시각은 검증하지 않았다. 함께 보는 것은 근거를 비교하기 위한 것이며 수신 시각을 실제 출력 발생 시각으로 바꾸지 않는다. 학습 전 필요한 시간 정렬·품질 검증은 별도다.

실제 출력은 드라이버에 적용한 소프트웨어 PWM 기록이다. 전기적 파형·실제 이동·물리적 정착을 보증하지 않는다. 실행 전 예측 입력은 현재 영상과 예정 명령이며 이후 센서·실제 출력은 학습 목표·평가·실행 검증 용도로 구분한다.

## 실패와 검증 범위

명령을 자동 재전송하지 않는다. 촬영 정지·부팅 변경·예상 밖 관절 출력·출력 순번 누락·저장 오류 시 추가 동작을 차단하고 부분 기록을 보존한다. 기존 수집기와 같은 전역 저널을 사용하며 출력 정지 미확인·종료 기록 누락은 재시작으로 자동 해제되지 않는다. 삭제나 새 ID 재실행으로 해소하지 않는다.

출력 정지가 이미 확인된 수집 대기 상태에서만 상태·출력 조회의 `RemoteDisconnected`를 한 번 재조회한다. 최초 요청과 재조회는 기존 0.8초 제한을 공유하며 실패·재조회 의도를 보존한다. 재조회 후에도 IDLE·센서 최신성·부팅 ID·출력 순번 연속성·비영 출력 검사를 그대로 통과해야 한다. 쓰기·구동 중 조회·종료 처리·시간 초과에는 이 복구를 적용하지 않는다.

기존 HTTP 제한 시간을 유지하기 위해 주 스레드에서 단발을 처리한다. **수집 중단은 진행 중인 단발 처리 이후 실행될 수 있으며 즉시 비상 정지가 아니다.** 브라우저가 사라져도 요청은 유한 시간이고 수집 예산은 유지된다. 강제 종료 시 다음 실행에서 미완료 저널을 보존한다.

저장 완료는 학습 적격 판정이 아니다. `datasetEligible=false`, `trainingPerformed=false`를 유지하며 자동 라벨 생성·학습·모델 배포는 하지 않는다.

```sh
python3 -m unittest tests.test_manual_collection tests.test_manual_collection_server tests.test_manual_collection_ui
```

모의 장치·카메라의 성공·실패·누락·재시작, 루프백 API, 원본 무결성 및 브라우저 스크립트를 검사한다. 브라우저 스크립트 검사는 Node.js가 필요하다. 모든 관절의 구동 검증을 뜻하지 않으며, 관절별 실물 결과는 아래에서 구분한다.

2026-11-04 실물 검증은 다음 두 기록을 구분한다. 기존 실패 기록을 재개하거나 성공으로 변경하지 않았다.

| 조건 | 촬영·센서 | 명령·종료 결과 |
| --- | --- | --- |
| 대기 조회 복구 적용 전 | 35프레임, M4 센서 7점 | 구동 전 출력 이력 GET 연결 종료. 동작 요청 0회, 종료 후 출력 0 확인 |
| 복구 수정 후 새 검증 | 138프레임·약 18.30초·누락 0, M4 센서 20점 | 대기 상태 GET 복구 2회 성공. 아래 20%·250ms 요청 1회, ARM 응답 연결 종료로 RUN 전송 0회. 종료 상태 GET 시간 초과로 세션 내 정지 확인은 실패 |

두 기록의 프레임 이미지·메타데이터 해시가 모두 일치하고 실패 기록을 화면에서 다시 확인했다. 센서 27점은 모두 223.68°이며 실제 이동·센서 정확도 검증은 아니다. 두 번째 기록의 GET 복구는 각각 약 0.376초·0.262초로 기존 0.8초 한도 이내였다. ARM 쓰기는 재전송하지 않았으며 STOP·큐 비우기·기본 출력 복원 응답을 보존했다.

두 번째 종료 이후 **별도 읽기 전용 확인**에서 같은 부팅·IDLE·5축 출력 0·빈 큐를 확인했고, 수집 시작 이후 새 출력 기록 10건도 모두 0이었다. 원래 세션의 `finalIdleOffVerified=false`와 실패 결과는 보존했다. 이후 전역 저널 잠금 아래 새 읽기 전용 확인으로 같은 부팅·IDLE·5축 출력 0·빈 큐·RUN 미전송·수집 이후 출력 0을 다시 확인하고, 별도 복구 근거를 저장해 새 수집 차단만 해제했다. 기존 요청을 재전송하거나 실패 기록을 성공으로 변경하지 않았다.

후속 비구동 비교에서 Mac 직접·SSH 터널·Pi 내부 경로 각각 상태·출력 조회 4회는 모두 0.8초 이내에 응답했다. 별도 진단 조회 전후의 빈 연결 해제 카운터는 4로 같았다. 작은 표본에서 오류가 재현되지 않았으므로 특정 경로나 서버의 첫 바이트 대기 종료를 원인으로 확정하지 않는다. 이 비교 당시 실제 구동·동작 전이 수집·모델 학습은 미완료였다.

이후 [단계별 TCP 계측](evidence/2026-11-04-http-response-gap.md)에서 직접 연결의 실패를 재현했다. 요청 수신 확인 전에 연결이 닫히는 경우와, 응답 헤더 이후 본문의 순서 구멍이 채워지지 않아 0.8초를 넘는 경우를 구분했다. 같은 응답이 1.889초에 완성되는 진단 사례도 확인했다. 물리적 손실 위치와 앞선 ARM 연결의 직접 원인 확정은 남아 있으며, 해당 진단 당시에는 실행 시간 제한·펌웨어·실패 판정을 변경하지 않았다. 후속 수정은 아래와 같다.

## 수집 통신 응답 축소

수동 수집은 `collection.v1` 상태 응답을 사용한다. 기존 안전 검사에 필요한 상태·5축 출력·센서 최신성·M4 경계와 각도·IMU 값을 유지하면서 응답 본문을 최대 1,200바이트로 제한한다. 기존 제어 화면의 `/status`는 유지한다.

출력 이력은 `/action_outputs?after=N&limit=8`로 최대 8개씩 읽는다. 최초에는 보존된 이력을 읽어 5축의 마지막 출력을 확인하고, 이후에는 순번·부팅 ID·시간 연속성을 검사한다. 누락이나 덮어쓰기로 현재 수집의 근거가 끊기면 중단한다. 각 HTTP 요청은 기존 0.8초 제한을 유지한다. 촬영·ARM 이전 최초 이력 읽기만 최대 4초·16페이지를 허용하고, 이후 대기·구동 중 페이지 묶음은 전체 0.8초·16페이지로 제한한다. 원본 페이지를 모두 저장한다.

서버의 첫 요청 바이트 대기는 100ms에서 500ms로 조정했다. 이는 관측된 239ms TCP 재전송 대기보다 여유를 주는 제한이며 통신 성공을 보장하지 않는다. 빈 연결이 다른 HTTP 요청을 늦출 수 있는 시간도 늘어나므로 HTTP 중단 버튼을 즉시 비상 정지로 해석하지 않는다. 명령 자동 재전송과 실행 제한 확대는 추가하지 않았다.

소프트웨어 검사·독립 리뷰·기본 및 finite 프로파일 펌웨어 빌드를 통과했다. 펌웨어를 한 번 업로드하고 새 부팅의 IDLE·5축 출력 0·빈 큐를 확인했다. 실제 수집 상태 응답 본문은 833바이트였다.

## 통신 수정 후 첫 저장 완료

2026-11-04 M4 아래 방향 20%·250ms 단발 한 번을 수동 수집 화면에서 요청하고 완료·저장했다. 새 시도 1회 중 1회 저장 완료이며, 앞선 실패 2회는 그대로 보존한다.

- 영상 239프레임·첫/마지막 PTS 간 약 31.733초와 M4 센서 45점을 저장했다. 이미지·메타데이터 478개 해시가 모두 일치했다.
- ARM 1회·RUN 1회이며 통신 오류·재조회·명령 재전송은 없었다.
- 실제 M4 드라이버 PWM은 −10→−20→−30→−40→−30→−20→0이었다. 첫 비영 출력부터 0까지 장치 시계상 322ms였다. 요청값 250ms·예상 PWM −51과 실제 출력 이력을 구분한다.
- 다른 관절의 비영 출력은 없었고 종료 시 IDLE·5축 출력 0을 확인했다. 저장 영상과 명령·출력 이력을 화면에서 다시 열었다.
- 센서 45점은 모두 223.68°였다. 기록된 센서에서 각도 변화가 검출되지 않았으며, 이 결과를 움직임 성공이나 센서 정확도 검증으로 표현하지 않는다.

촬영기는 60초 한도 전에 운영자가 종료해 원본 종료 상태를 `partial`로 보존한다. 수집 세션의 `completed`는 요청 처리·저장·최종 정지 확인의 완료를 뜻한다. 학습 적격 판정과 실제 학습은 수행하지 않았다. 이 한 번의 완료로 통신 문제가 모두 해소됐거나 M1~M5 전체가 검증됐다고 판단하지 않는다.

## 출력을 높인 후속 수집

같은 날 아래 방향 요청을 25%·350ms로 높여 새 기록 한 번을 수집·저장했다. 센서 각도는 **223.68°에서 222.36°로 1.32° 감소**했다. 출력 비율과 요청 시간을 함께 바꿨으므로 각각의 영향이나 최소 구동 조건을 이 한 번으로 분리하지 않는다.

| 항목 | 후속 수집 결과 |
| --- | --- |
| 영상 | 256프레임, 첫/마지막 PTS 간 약 34.100초 |
| 센서 | 48점, 시작 223.68°·종료 222.36° |
| 요청 | M4 아래 25%·350ms, ARM·RUN 각각 1회 |
| 실제 드라이버 출력 | PWM −10부터 −60까지 상승 후 감소·0, 비영 구간 548ms |
| 오류·재전송 | 없음 |
| 종료 | IDLE·5축 출력 0·빈 큐 |

요청의 예정 PWM −63·350ms와 실제 최대 크기 60·548ms는 서로 다르며 원본에 함께 남겼다. 다른 관절의 비영 출력은 없었다. 영상·명령·출력 이력을 화면에서 다시 열었다. 센서에서 변화가 관측된 기록이며, 영상 기반 각도 계측과 센서의 정확도·장치 간 시계 정렬을 검증한 결과는 아니다.

통신 수정 후 두 수집은 모두 저장 완료했고 그중 한 수집에서 센서 변화가 관측됐다. 수정 전 실패 두 기록도 보존한다. 반복 재현성·학습 적격 판정·모델 학습은 아직 미완료이며, 다음 단계는 같은 25%·350ms 조건에서 반복 기록을 확보해 변화의 분포를 확인하는 것이다.

## 같은 요청의 추가 3회 반복

같은 25%·350ms 아래 방향 요청을 3회 더 수집했다. 추가 3회 모두 저장·종료 정지 확인이 완료됐고, 직전의 같은 요청 1회까지 합쳐 비교 가능한 기록은 4회다. 실패를 새 ID로 대체하거나 명령을 재전송하지 않았다.

변화량은 각 기록에서 **명령 의도 기록 직전 마지막 센서 5점의 중앙값 − 출력 정지 확인 후 마지막 센서 5점의 중앙값**으로 계산했다. 원시 센서값은 보존하며 중앙값 요약을 센서 정확도 개선으로 해석하지 않는다.

추가 3회의 평균 감소량은 **1.26°**, 최소·최대는 **1.14~1.32°**, 범위는 **0.18°**였다. 직전 기록을 포함한 4회 평균은 1.275°다. 네 번 모두 아래 방향 변화가 나타나 이번 좁은 자세 구간에서는 결과가 비교적 비슷했다. 그러나 시작 자세를 되돌리지 않은 순차 관측이며, 동일 시작 상태의 반복 정밀도나 일반적인 성공률을 검증한 시험은 아니다. 0.18°도 예측 신뢰구간이 아니다.

최대 PWM 크기는 네 번 모두 60이지만 실제 비영 출력 구간은 434~548ms로 달랐다. 같은 요청 시간이 같은 출력 파형·출력 기간을 보장하지 않으므로 실제 출력 이력을 학습 사후 근거로 유지한다. 각 기록의 통신 오류·재조회·명령 재전송은 없었고 다른 관절의 비영 출력도 없었다. 최종 상태는 IDLE·5축 출력 0·빈 큐다.

다음 단계는 이 네 기록의 영상과 명령·센서·출력을 시간 기준에 맞춰 정렬하고 첫 데이터셋의 품질을 판정하는 것이다. 자동 학습은 아직 실행하지 않았다.
