# Embedded Bring-Up

[README](README.md) | [ROBOTICS_SYSTEM_READINESS](ROBOTICS_SYSTEM_READINESS.md)

This document summarizes the embedded evidence for firmware-heavy robotics
roles. It is intentionally specific about what is implemented and what still
needs measurement evidence.

## Hardware Roles

| Layer | Board | Responsibility |
| --- | --- | --- |
| Motion controller | ESP32 Dev Module | 5-axis motor output, safety state, command dispatch, web UI, Wi-Fi |
| Sensor/teleop controller | STM32F446 | MPU-6050, UART sensor/teleop frames, timer-driven firmware path |
| Camera node | ESP32-CAM | capture, stream, camera profile endpoints |
| Host | Raspberry Pi 4 | dashboard, perception service, ROS2 Jazzy bridge |

## Implemented Interfaces

ESP32 controller:

- TB6612FNG x3, five DC motor outputs.
- PWM configured at 1 kHz with 8-bit duty.
- `BOOT -> IDLE -> ARMED -> FAULT` state boundary.
- `Dispatcher` + `SafetyGate` shared by serial and HTTP commands.
- hard stop, emergency stop, teleop frame timeout, and deadman release paths.

STM32 sensor/teleop firmware:

- STM32F446 HAL project generated by CubeMX.
- I2C path for MPU-6050.
- USART path for structured JSON-like frame output.
- TIM/DWT timing support in firmware.
- HC-SR04 firmware path exists, but final physical demo treats range telemetry
  as disabled/nonblocking because the sensor is not installed.

Camera and host:

- ESP32-CAM `/status`, `/capture`, `/stream`, `/camera`.
- Pi perception service with color tracking and constrained known-object `cup`
  detection path.
- ROS2 bridge from controller/dashboard/perception state into typed topics.

## Timing And Safety Claims

Use these claims:

- bare-metal/HAL superloop plus timer interrupt firmware, not RTOS.
- open-loop DC motor control with safety gating, not encoder-grade joint servo.
- constrained known-object perception and target alignment, not arbitrary object
  recognition or autonomous grasping.
- operator-confirmed or dry-run routine planning, not unchecked autonomous
  execution.

Do not claim:

- RTOS porting.
- CAN, USB, Ethernet, or SPI production implementation.
- EMI/EMC certification work.
- production/DFM ownership.
- vendor-specific smart-actuator integration.

## Measurement Checklist

Capture these before an embedded-focused interview if hardware is available:

| Signal | Expected evidence | Tool |
| --- | --- | --- |
| Pi SSH/network | alias resolves to the current Pi, TCP/22 reachable, SSH service/socket active | `tools/raspi/check_pi_ssh_target.py` |
| ESP32 PWM | 1 kHz PWM, duty changes with percent command | oscilloscope or logic analyzer |
| UART link | 115200 baud STM32-to-ESP32 frame stream | logic analyzer |
| I2C bus | MPU-6050 SCL/SDA activity during firmware loop | logic analyzer |
| Motor power | voltage drop during bounded joint pulse | multimeter |
| Deadman release | release-to-stop latency and final motor stop state | video plus serial log |
| Sensor stale | stale frame causes blocked motion | serial log or dashboard screenshot |
| ROS2 bridge | typed status/detection/guard samples | `tools/raspi/capture_ros2_evidence.sh` |

Record measured values in a dated note under `docs/` or curated public evidence.
Do not move raw local captures into git unless they are reviewed and small.

## Bring-Up Commands

ESP32 controller build:

```bash
pio run
```

ESP32-CAM build:

```bash
pio run -d firmware/esp32cam
```

STM32 helper scripts:

```bash
tools/stm32_build.sh
tools/stm32_upload.sh
tools/stm32_build_upload.sh
```

Host contract tests:

```bash
python3 -m unittest discover -s tests
```

## Failure Notes To Explain

- GPIO strapping pins were avoided in the motor-driver pin map.
- ESP32-CAM QVGA is good enough for constrained bench perception but weak for
  general object recognition.
- The low-cost arm lacks encoders, force sensing, and absolute joint feedback.
- Physical routine execution is disabled until feedback readiness and validation
  justify enabling it.
- HC-SR04 is not part of the final mounted physical demo.
